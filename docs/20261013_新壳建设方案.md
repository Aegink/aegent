# 新壳建设方案：React 19 + shadcn/AI-Elements 组件底座 + 多仓设计融合（2026-10-13）

> 用户决策与诉求：技术栈定为 **React 19 + 自写组件**；最看好 **ZCode** 的壳；
> 目标"吸取各仓优点做一个自己的"。本文是全面评估与实施方案（先评审、后动工）。
> 事实来源：逐仓核查（oss/ 快照）+ 我方协议/UI 现状实测（本文所有数字均有出处）。

---

## 一、结论先行

**"整体拿某个仓的壳直接改"不成立，但"用 zcode 的组件底座 + 多仓设计融合"是一条
真实可行且最省力的路。** 关键结论三条：

1. **ZCode 的可复用面不在"应用层"而在"组件底座"**：它的 UI 是标准的
   **shadcn/ui 模式**（`components.json`: style=radix-mira / Tailwind cssVariables /
   iconLibrary=**lucide**）——`src/components/ui/` **45 个 shadcn 组件** +
   `src/components/ai-elements/` **46 个 AI 对话组件**（Vercel AI Elements 体系），
   全部是**源码复制式组件**——可直接进我们的项目（shadcn/AI-Elements 为 MIT，
   zcode 定制部分 Apache-2.0，均允许复制，登记即可）。
2. **它的应用层（1550 文件）与协议层（74 方法 ZCodeProtocol）不可搬**：应用层
   深度绑定 `@zcode/services` + `@zcode/rpc`（62 依赖树，含 stripe/文档渲染等
   无关功能）；协议翻译器要覆盖 74 个方法（含我们没有的 computer-use/automation/
   provider-headers 面）——工作量超过自研。
3. **我们自己的接缝与功能基线已就绪**：host 侧四信封 WS 协议 + 7 个 query op +
   **60+ 个 settings op**（文件树/git/插件市场/供应商测试/数据中心/日志/定时/
   协作派发全在）；现有 ui/ 23,066 行是**功能对齐基线**（新壳按它逐项对齐，
   但不搬它的实现）。

**推荐路线（本方案主体）**：
> **React 19 + Vite + TS + Tailwind + Radix + lucide**（与 zcode 技术栈同构）——
> 组件底座直拿 zcode 的 shadcn/AI-Elements 91 件 + 设计蓝本以 zcode 为主
> （布局/设置中心/交互）+ opencode（diff/会话视图）与 pi-desktop（审批/工具卡，
> 我方已借鉴）为辅 + **自写四信封数据适配层**（不可省，约 3k 行）——现有 ui/
> 保留并行、逐面板切换、随时可回退。

## 二、事实核查（三条决定路线的发现）

### 2.1 "整体套壳"三仓逐验

| 仓 | 想套它要做什么 | 实测代价 | 判定 |
|---|---|---|---|
| **zcode** | ①写协议翻译器对接它的壳（74 方法 ZCodeProtocol + `@zcode/rpc` channel 面）；或 ②搬 ui 包改造 | ①74 方法映射 ≥ 自研 UI；②62 依赖（stripe/lexical/pptx-docx-xlsx 渲染等无关功能）+ 1550 应用层文件删改 + 数据层（services/descriptor/broadcast）全重写 | **不划算** |
| **opencode** | 搬 app/ui（SolidJS） | 组件库真解耦（peer 仅 solid-js），但**与已选 React 栈冲突**；app 数据层（sdk/event/sync）须重写 | 组件可参考，栈不匹配 |
| **pi-desktop** | 搬 Electron+React 壳 | LGPL-3.0（复制分发须回馈修改）+ 87k 行绑 RACP/agent-runtime | 仅抄设计（既有纪律） |

**根因（通用）**：每个壳的 UI 都是其自身数据模型的投影层——换后端必重写该层；
且体量倒挂（拷 30 万行适配 4 万行内核）。

### 2.2 可直拿的组件层（本次核查的最大收获）

**zcode = shadcn/ui 标准工程**（这是"源码即组件"的复制式体系，天然可移植）：

| 资产 | 内容 | 量 | 许可 | 用法 |
|---|---|---|---|---|
| `packages/ui/src/components/ui/` | shadcn 标准组件 + zcode 增强件（button/card/dialog/context-menu/command/**code-viewer/diff-viewer/pdf-viewer**/kbd/popover/…） | **45 件** | MIT(shadcn)/Apache(zcode 定制) | 源码复制 |
| `packages/ui/src/components/ai-elements/` | **AI 对话组件**（agent/conversation/**confirmation/connection/checkpoint**/attachments/code-block/markdown 族/…） | **46 件** | MIT(Vercel AI Elements)/Apache | 源码复制 |
| `components.json` + `lib/utils.ts` | shadcn 配置与 cn 工具 | — | 同上 | 配置同构 |
| 主题体系 | Tailwind cssVariables + baseColor=neutral + **lucide 图标**（与我方现有 UI 同源） | — | — | 沿用/调整 |

**opencode 的对应资产**（备选参考，SolidJS 栈）：`packages/ui` 133 组件三件套
（含 css/stories）+ `session-ui` 95 件——**组件设计**可抄（如 diff-changes、
message timeline），代码因栈不匹配不做直拿。

### 2.3 我方接缝与基线（新壳的"地皮"）

- **协议**：WS 四信封（hello/request/response/event）——客户端实现参考 `ui/api.js`
  （132 行，含连接/重连 3s/requestId 关联/三类信封）；prompt=`{type:"prompt",
  messageId, content}`；审批=`{type:"approve", requestId, action, scope?, source}`。
- **服务面**：query 7 op（sessions/search/files/meta/review/file/usage）+
  settings 60+ op（fs 树/git 全操作/插件与市场/供应商测试/技能/提示词/数据中心/
  日志/关于/终端/检查点/WebDAV/定时/collab 派发）——**新壳的能力上限已经就位**，
  不需要内核侧新开协议。
- **事件面**：33 类事件闭集（turn/step 生命周期、user/assistant 消息、tool 调用
  与结果、compaction/checkpoint、model/switch、approval 相关、collab 等）——
  适配层按此做 reducer 映射。
- **功能基线**：现有 ui/ 55 文件 23,066 行——覆盖对话流/composer/审批/设置中心
  （13 分节）/文件树/评审/Git/浏览器/助手面板/语音/数据中心/插件中心/技能/提示词/
  调度/导出导入。**新壳分期对齐这份清单**（清单即验收表）。

## 三、方案设计

### 3.1 技术栈（与 zcode 同构）

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | **React 19**（用户已定） | zcode/hermes/pi-desktop/pideck 同栈，参考做法最多 |
| 构建 | **Vite**（TS） | zcode 同款；dev 热更 + 静态产物 |
| 样式 | **Tailwind CSS v4 + cssVariables 主题** | zcode 同款；变量体系便于换肤（我们已有主题变量实践） |
| 组件基座 | **Radix（radix-ui 统一包）** | shadcn 的底层；无障碍与键盘交互免费获得 |
| 图标 | **lucide** | 与现有 ui/ 同源（已做过图标数据提取） |
| 语言 | 简体中文为主 + i18n 键（沿用现有 locales 结构） | 现有资产 |

### 3.2 分层架构

```
web/                          新壳（与现有 ui/ 并行，host 与内核零改动）
├── src/
│   ├── protocol/             四信封客户端（TS 化重写自 ui/api.js）
│   │   ├── types.ts          信封/事件类型（客户端视角镜像）
│   │   └── client.ts         WsClient：连接/重连/hello/request/settings/query/订阅
│   ├── adapt/                ★ 数据适配层（自写核心，不可省）
│   │   ├── view-model.ts     33 事件 → 视图模型 reducer（消息/工具卡/审批卡/状态）
│   │   ├── use-session.ts    React 绑定（事件流 → 组件树）
│   │   └── ops.ts            settings/query op 的 TS 封装（60+ op 按面分组）
│   ├── components/           ★ 复制自 zcode（45 shadcn + 46 ai-elements，登记后带版权头）
│   ├── views/                组装层：对话流 / 审批 / 设置中心（13 分节对齐）/
│   │                         文件树 / 评审 / Git / 用量 / 插件中心 …
│   ├── styles/               Tailwind 主题（cssVariables，暗亮双态）
│   └── App.tsx               布局骨架（侧栏 + 主区 + 状态条）
└── vite.config.ts            dev：直连 host（ws://127.0.0.1:8787/ws）；build：静态产物
```

**数据流（与内核投影思想同构）**：
`host 事件流 → WsClient 订阅 → reducer 累积视图模型 → React 渲染`；
历史恢复 = 拉 `query{op:"events"}` 全量事件 → 同一 reducer 重放（离线可重放、
测试可快照——与内核"投影从流重建"完全一致的架构，这是我们的主场）。

### 3.3 各仓优点的吸收清单（用户核心诉求）

| 抄什么 | 从哪 | 形式 | 说明 |
|---|---|---|---|
| 组件底座（91 件） | **zcode** | **代码直拿**（Apache/MIT） | shadcn + AI Elements 源码复制 |
| 产品布局/信息架构 | **zcode** | 设计 | 侧栏+主区结构、设置中心分节、对话流组织 |
| 设置中心 13 分节结构 | **zcode**（其设置面）+ 我方现有分节 | 设计+对齐 | 现有 settings/ 13 文件即分节清单 |
| 工具调用/思考块/审批卡交互 | **pi-desktop**（既有借鉴）+ zcode `confirmation.tsx` | 设计 | 我方已有成熟交互模式记录 |
| diff/代码/审查视图 | **opencode**（diff-changes 设计）+ zcode `diff-viewer.tsx` | 设计+组件 | zcode 组件可直接用 |
| 多会话工作台 | **pideck** | 设计 | 会话卡片/状态/并行管理 |
| 键盘驱动交互/命令面板 | **zcode**（command.tsx 已在组件底座）+ pi TUI 习惯 | 组件+设计 | 命令面板直接用 shadcn command |
| 终端面板 | **zcode**（xterm 依赖模式）/ qwen | 依赖+设计 | @xterm/xterm 直接引（MIT） |
| Markdown/代码高亮/数学/Mermaid | zcode 依赖树（streamdown/shiki/katex）| 依赖直引 | 均为独立 MIT 库，直接 npm 装 |

### 3.4 功能分期（对齐现有 ui 基线）

| 期 | 范围 | 出口标准 |
|---|---|---|
| **P0 对话闭环** | 连接/hello/历史恢复/发消息/流式渲染（assistant 消息）/工具卡（call+result 配对）/审批卡（allow/deny/scope）/中断/重连 | 与 host 真机联调：完整跑一轮含工具与审批的对话 |
| **P1 日常可用** | 会话列表（sessions op）/模型切换（setModel 信封）/设置中心骨架（basic/providers/core）/文件树（fs-tree）/命令面板/主题 | 日常使用可替代旧 UI 主路径 |
| **P2 全量对齐** | 设置中心 13 分节补齐/评审/Git/用量/插件中心与市场/技能/提示词/调度/数据中心/日志/检查点/协作面板/导出导入 | 逐项对照现有 ui 清单打勾 |
| **P3 增强** | 多会话工作台（pideck 形态）/浏览器面板/语音/快捷键体系/移动端适配 | 差异化体验 |

### 3.5 里程碑与工作量（估算）

| 阶段 | 内容 | 估算 |
|---|---|---|
| M0 骨架 | Vite+React+Tailwind+Radix 工程 + 组件底座导入（91 件）+ 协议客户端 + 主题 | 1~2 天 |
| M1 适配层 | reducer + hooks + op 封装（33 事件/7 query/60+ settings 的 TS 面） | 2~4 天（≈3k 行） |
| M2 P0 闭环 | 对话流/工具卡/审批卡/输入框 | 2~3 天 |
| M3 P1 | 会话/设置骨架/文件树/命令面板 | 3~5 天 |
| M4 P2 | 13 分节与全部面板对齐 | 5~10 天（可分批） |

对比现状：现有壳 23k 行手写承载同样功能；新壳中渲染与无障碍由组件底座承担，
**我们自己写的只有适配层（~3k）+ 组装（~5k）**，且后续每加一个功能是"拼组件"
而不是"手写 DOM"——直治痛点 1（样式布局）/2（手写交互）/3（功能速度）。

## 四、风险与决策点

| # | 风险 | 缓解 |
|---|---|---|
| 1 | 组件复制后的"许可混血"（shadcn MIT + zcode Apache + Vercel MIT） | 逐文件保留原始版权头 + THIRD_PARTY 登记（含 zcode NOTICE.md 相关段）+ 复制清单入册 |
| 2 | 91 组件引入的依赖增量（Tailwind/Radix/@pierre/diffs/streamdown/shiki…） | 按需引入：只复制用到的组件与其依赖；纯展示组件零运行时依赖 |
| 3 | 适配层语义偏差（事件→视图的边界情形：取消/重试/压缩/换模） | 以现有 ui 行为为基线做对照；reducer 纯函数可快照测试（我方测试体系强项） |
| 4 | 双壳并行期的心智负担 | 阶段切换：P1 后用新壳替代主路径、旧壳冻结；URL 参数/构建标志切换 |
| 5 | 桌面壳（Tauri）与新壳的衔接 | 新壳产物仍为静态文件，Tauri 侧零改动（沿用现有打包链）；qwen 的"Tauri 薄壳"可作参考 |
| 6 | 组件视觉与现有品牌（暗色+变量主题）不一致 | M0 先定主题 token 映射（zcode neutral base + 我方品牌变量），组件样式统一过一遍 |

**决策点**（动工前确认）：
1. 目录名与形态：`web/`（推荐）还是替换 `ui/`（建议并行不替换）；
2. Tailwind 还是沿用现有 CSS 变量手写样式（推荐 Tailwind——与组件底座同构）；
3. 设置中心是否首期就做（建议 P1 骨架、P2 补齐——对齐 13 分节）。

## 五、许可合规（强制项）

- **可复制**：zcode（Apache-2.0——保留 LICENSE/NOTICE 摘要、文件头声明）、
  shadcn 组件（MIT）、Vercel AI Elements（MIT）、opencode 组件（MIT，若采用其设计稿）。
- **禁止复制**：pi-desktop 代码（LGPL——继续只抄设计）；claude-code（专有——只读行为）。
- **动作**：新壳目录下加 `THIRD_PARTY-NOTICES.md`（逐组件来源 + 许可 + 是否修改）；
  主仓 THIRD_PARTY.md 追加登记；复制文件保留原始版权头（项目既有铁律）。

## 六、验收标准

1. **P0 真机闭环**：起 host → 新壳连接 → 发消息 → 流式渲染 → 工具卡 → 审批
   （含 scope=session/always）→ 回合结束；断线重连与历史恢复（query events 重放）正确；
2. **行为对照**：P0~P2 每个面板与现有 ui/ 逐项对照（清单即上表分期）；
3. **工程**：tsc 0 error + 构建产物可被 Tauri 承载 + 与 host 协议零变更（内核零改动）；
4. **合规**：THIRD_PARTY-NOTICES 完整、版权头保留、复制清单可审计。
