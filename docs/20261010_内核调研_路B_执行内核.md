## §10 与"0 底座 + 万物可插件"的边界结论

| 层 | 落点 | 我方现状 | 建议 |
|---|---|---|---|
| **0 骨架** | 进程/装配/事件/协议/包边界 | `src/kernel/events.ts`(934)、`agent-protocol.ts`(1094)、`plugin-loader.ts`/`plugin-manifest*.ts` 已具形；但**包边界为 0**（单包 src/） | 立包边界（B5 起步）：至少 kernel / models / context-engine / policy-rules 四包 |
| **一 原语** | **循环 + 会话** | `loop.ts` + `session/`(8964) 都在内核 ✓ | 循环必留；只把**护栏实现**搬出（B7） |
| **二 派生原语** | **工具** / 子代理 / 编排 / 渠道 | 工具契约+注册表在内核 ✓（正确）；调度**缺**（需补 B2）；32 个工具实现**全在内核**（过重，B3） | 契约+调度留内核；**工具实现**下沉（B3） |
| **三 万物** | 全部插件 | 已有 plugin-manifest/scaffold/contributions 骨架，但内置工具/压缩/审批规则未走插件化 | 按 B3/B4/B6 分批下沉，插件失败=回落内核默认 |

**最终回答**：参考仓的一致边界是——**循环 + 工具契约 + 调度骨架在内核（一 + 二的接口面），工具实现 / 压缩引擎 / 审批规则 / 模型 wire 适配在包或插件（三）**。我方当前把"接口面"和"实现面"混在同一目录（tools/builtin、context、policy 全在 kernel 邻域），因此**看起来重**；真正缺的不是精简，而是**边界与调度原语**。
