## 0. 决策摘要（先看这一页）

### 0.1 五条核心结论

1. **参考仓的"0"不是"最小行数"，而是「最小语义面 + 装配全外置」。**
   三种范式：pi 把内核压到 6 文件 2,519 行（连 `/mcp`、codemode 都是"可被第三方接管的内置扩展"）；
   dsh 用 331 个包 + 一份 YAML 把装配变成数据（内核只是 Service 仓库）；
   pi-desktop 内核直接外包上游 pi 两包，自写"无传输语义核 2.5K + 无 Electron 运行时 6.1K"。

2. **我方内核的问题不是"重得离谱"，而是「形状不均 + 边界缺失」。**
   - **过重**：`src/kernel/` 21,978 行（pi 内核的 8.7 倍）；kernel 直接声明依赖 8 个域
     （`architecture-policy.json` kernel.requires）+ 未声明的 scheduler——**它是"装配中心"而不是"骨架"**。
   - **过轻**：工具契约只有 8 字段（`ToolDef`），**没有调度原语**（只有 `parallel` 二值 + 一把 RwLock）。
   - **缺口径**：编排/子代理/记忆/渠道——**引擎都在，方向盘不在模型手上，且不能外置**。

3. **依赖治理的"标准答案"我方已经有模板（zcode 同源），但没对自己下狠手。**
   现状 `node tools/architecture-check.mjs` = **1 error / 42 warning**，且 kernel 是依赖环上的节点却
   `managed:false`（违规只降级 warn）。参考仓里 zcode 用同一套策略但 `forbidCycles:true` + `managedOnly:true` 硬失败。

4. **"模型可发起编排" ≠ "编排要在内核里"。**
   参考仓全部把编排接到模型手上（zcode `Agent`/`SendMessage`、dsh `send_message`/`workflow`、
   pi-desktop `SessionTask`、agentscope `_TeamAssign`），**但编排工具几乎全在插件层**——
   pi-desktop ADR 0237 明确把 orchestration 做成**普通市场插件**，host 只留两个原语 + 一份通信账本。
   我方恰好做反了：**服务库 + 事件账本在内核，工具与模型入口为零**（唯一入口是 UI settings op）。

5. **真正缺的不是"精简"，是「边界 + 注册面 + 调度原语」。**
   我方所有域的"端口"都已存在且质量高（`SandboxBackend`/`ImSurface`/`SchedulerRuntime`/`LspClient`/
   `McpConnection`/`ToolDef`/`EVENT_TYPES`），但**"注册面"全缺**——所有绑定都发生在装配期三处硬编码，
   所以"外置"等价于"改装配代码"，而不是"装一个包"。

### 0.2 分期路线一句话（详见 §6）

**治标先治本、先零风险后重构**：
- **P0（立即，零风险）**：治理收紧（kernel 环硬失败、修 1 error）→ 给编排装方向盘（模型工具，引擎现成）
  → 补 IM allowlist（安全）→ 记忆 provider 抽象（样板级外置）。
- **P1（边界与契约）**：工具契约补元数据 → 提取 ToolScheduler → loop 护栏搬家 → 模型适配抽包
  → 子代理 resume/send_message。
- **P2（外置）**：内置工具分批插件化 → 压缩引擎下沉 → 渠道外置 → 审批规则外置。
- **P3（择机）**：会话库分域、会话类型闭集、fan-out 脚本编排（**本期不做**）。

## 1. 坐标系：四层框架与三种"0 底座"范式

### 1.1 判定框架（用户理念 → 工程分层）

| 层 | 含义 | 应留内核 | 判据 |
|---|---|---|---|
| **0 = 道（骨架）** | 进程 / 装配 / 事件 / 协议 / 包边界 | ✅ 必须 | 一切插件共享的"公共语言"与"进程边界" |
| **一 = 基本原语** | **agent 循环 + 会话** | ✅ 必须 | 少了它不成 agent（pi 内核只留这两样） |
| **二 = 派生原语** | 工具 / 子代理 / 编排 / 渠道 | 接口留、**实现外置** | 契约是骨架，实现是插件 |
| **三 = 万物** | 全部插件（记忆/压缩/审批规则/主题/IM/…） | ❌ 外置 | 参考仓一致把实现放包/插件 |

### 1.2 三种"0 底座"范式（可直接抄的答案）

**(a) pi —— 最小语义面 + "内置即可替换的扩展"**
内核 `packages/agent` 只 6 文件 2,519 行（循环 + 事件类型 + `StreamFn` 契约），依赖仅 `pi-ai` + `typebox`。
连 `/mcp`、codemode、tool-search 都是**与第三方同一接口、同一声明数组**的内置扩展，还显式标 `replaceable: true`
（第三方 MCP 扩展"接管"而非并存）。
锚点：`oss/pi/packages/agent/src/index.ts:1-5`；`oss/pi/packages/coding-agent/src/extensions/index.ts:6-13`。

**(b) dsh —— 装配即数据（最强"万物可插件"）**
331 个子包（一个工具一个包、一个 UI 面板一个包），默认组合是一份可被用户 patch 覆盖的 YAML
（94 行 insert / 517 行）；内核只是 Service 仓库 + 生命周期。装配顺序"不承载语义"（服务可用性驱动）。
锚点：`oss/deepseek-harness/packages/bundle/base/cordis.patch.yml:1-6`；`pnpm-workspace.yaml:2`。

**(c) pi-desktop —— 上游内核 + 本地薄运行时 + 捆绑插件走公共通道**
内核是别人的 `pi-ai`/`pi-agent-core`（ADR 0002）；自己只写 `agent-host`(2,459，无传输) +
`host-runtime`(6,104，无 Electron)。**捆绑插件（`pi.files`/`pi.browser`）走与第三方完全相同的公共通道**，
ADR 0105 明确拒绝"给捆绑插件私有能力"（"a private channel would not test the public plugin API"）。
锚点：`oss/pi-desktop/docs/adr/0284-headless-runtime-boundary.md`、`docs/adr/0002-use-pi-agent-harness.md`。

**反例（对照组）**：codex `core` 单 crate 250,171 行 / 583 文件（"插件"只到声明式资源包层，所以 core 必须自己扛）；
opencode `core` 32,993 行且 `package.json` exports 允许 `"./*": "./src/*.ts"`（**任意深导入，边界几乎不存在**）。

### 1.3 依赖治理的四种做法（我方该抄哪一档）

| 仓 | 强制手段 | 自动化 | 环治理 | 锚点 |
|---|---|---|---|---|
| **zcode** | `architecture-policy.yaml` + `scripts/architecture/*` | **是**（pre-push gate） | `forbidCycles:true` + `managedOnly:true`（未 managed 降级 warn）+ `requires` 白名单 + `publicEntrypoints` 禁深导入 + `layers/layerOrder` | `oss/zcode/architecture-policy.yaml:1-80`；`scripts/architecture/policy.mjs:46-66` |
| **pi** | `check-entry-graphs.mjs`（**入口点=成本契约**：每入口最大文件数 + forbid 清单） | 是 | 不查环，查"入口图的代价" | `oss/pi/scripts/check-entry-graphs.mjs:1-50` |
| **dsh** | `check-workspace-constraints.ts` + pnpm 约束 | 是 | 无环检测（依赖由 cordis `inject` 运行时驱动） | `oss/deepseek-harness/scripts/check-workspace-constraints.ts` |
| **opencode** | **仅 AGENTS.md 文字规则** | **否** | 无 | `oss/opencode/AGENTS.md` |

**关键**：我方 `tools/architecture-check.mjs` 头注自述"渐进采用（zcode 同语义）"——**策略同源，但没对自己下狠手**
（kernel `managed:false` → 环与超限全降级 warn）。**pi 的"入口预算"是"为 0 底座服务的治理"，最值得补**。

### 2.1 "模型能否发起编排"——逐仓判定（本报告最重要的一张表）

| 仓 | 模型能否发起 | 模型可见的编排工具 | 编排逻辑放在哪 | 锚点 |
|---|---|---|---|---|
| **我方** | ❌ **不能** | 无（`session_query`/`session_get` 只读） | 服务库 `collaboration.ts` + host `collab-runtime.ts`；入口=UI settings op | `src/host/protocol-settings.ts:109`；`ui/views/work.js:330-343` |
| zcode | ✅ | `Agent`/`SendMessage`/`TaskOutput`/`ReadSessionContext`/`CreateWorkflow` | 执行层 core（tools + subagent runner + workflow 子进程） | `oss/zcode/apps/zcode-cli/packages/core/src/tool/handlers/agent.ts:227`、`send-message.ts:48` |
| pi | ✅（扩展层） | `subagent`（前台）、`research`（后台+回投） | **扩展（插件）**；内核只给 conversation/task/submission | `oss/pi/packages/coding-agent/src/experimental/durable/subagent.ts:26` |
| pi-desktop | ✅（**官方插件**） | `SessionTask`（spawn/send/supervise/status/wait/result/accept/cancel/list） | **普通市场插件**；host-core 只加 `session/create` + `session/open` | `oss/pi-desktop/docs/adr/0237-session-orchestrator-as-a-plugin.md`；`adr/0239-...md` |
| dsh | ✅ | `subagent` + `send_message`/`interrupt_agent`/`list_agents`；`workflow` | 服务契约在核内，工具/provider 在**独立包** | `oss/deepseek-harness/packages/subagent/README.md`、`workflow/README.md` |
| hermes | ✅ | `delegate` + steer/interrupt/list | 工具层 | `oss/hermes-agent/tools/delegate_tool.py:1-11` |
| agentscope | ✅ | `_TeamAssign`（leader 指派具名 member） | 库级 Pipeline | `oss/agentscope/src/agentscope/pipeline/_team_pipeline.py:51-110` |

**pi-desktop ADR 0237/0239 = 本报告最重要的边界裁定**（摘）：
```
ADR 0237: Ship pi.session-orchestrator as an ordinary marketplace plugin. It registers the
SessionTask Agent Tool with spawn/send/supervise/status/wait/result/accept/cancel/list.
Two additive host primitives: (1) session/create 接受 inheritPermissionFromSessionId
（host 在持状态锁时复制父权限模式，调用者永不提交任意 worker 权限模式）；(2) session/open。
No Rust schema migration / message bus / DAG / change to Task family is added.

ADR 0239: host-core owns a durable session communication ledger keyed by message ID.
The host authenticates the sending Session ID from a correlated plugin tool invocation;
plugins cannot supply a forged sender. Permission checks remain host-owned; session
messaging cannot raise a target's effective permission above the initiating ceiling.
```

**结论**：编排的三层职责切分 = ①**原语**（建/开会话、发 prompt、观察 turn 终态、权限上限）留内核/host；
②**账本**（投递 id、源/目标、绑定真实 turn、完成回调、发起者身份校验）由 host 拥有且不可伪造；
③**工具**（模型可见的 spawn/send/wait/list 壳）**在插件**。
我方 ①✅ ②✅（甚至比 pi-desktop 更早做成事件双流）③❌——**是"缺口径"而非"缺引擎"**。

## 3. 三个纵深专题

### 3.1 专题一：装配边界（"0"最核心的问题）

**参考仓判据**：pi = "能不能被替换"；pi-desktop = "需不需要 Electron"；zcode = "CLI 要用的进 core，桌面管控的进 services"；
dsh = "没有内核，只有 Service 契约"；codex = "能抽成 crate 就抽"（但 core 仍 250K 行）。

**我方现状（实证）**：
- `architecture-policy.json` 中 kernel `managed:false`，且 `requires` 未列 scheduler；
- `src/kernel/agent-process.ts:69-72` **直接 import** `../scheduler/browser.js|browser-panel.js|computer.js|computer-win32.js`
  （未声明依赖，arch check 报 warn）——kernel 依赖 scheduler 的实证；
- `src/kernel/assembly.ts:47-53` 直接 import `../sandbox/containment.js`——kernel 依赖 sandbox 的实证；
- 反向依赖：`src/mcp/ws-plugin.ts:24` import `../host/protocol.js`（协议适配器依赖顶层 host）。

**结论**：kernel 必须**只依赖** kernel/* + provider 接口 + store 接口 + 事件词汇；所有域装配移出 kernel 到
`src/assembly/`（或 host）。目标规模：剥离域装配后 kernel 可压到 **~8,000 行**（现 21,978），
接近 pi-desktop 的"语义核 2.5K + 运行时 6.1K"量级。

### 3.2 专题二：工具契约与调度（"一生二"的关键缺口）

**zcode `ToolEntry` 是声明式厚契约的极参照**（`oss/zcode/.../core/src/tool/types.ts:68`）：
`name/description/modelInstructions/allowedInPlanMode/readOnly/destructive/concurrentSafe/requiresUserInteraction/
timeoutMs/maxOutputBytes/sideEffectScope/riskLevel/needsApproval/providerVisible/stopTurnOnSuccess/mcpPresentation`
+ `handler/schemas/permission/budget/timeout/cancellation/trace` 回调族。
**声明即契约**——元数据被**执行/调度/审批三处共读**（`registry.ts:104-129` 投影给 provider；`scheduler.ts:98-102` 判并行；
`permission-flow.ts:45` 判风险）。

**我方 `ToolDef` 只有 8 字段**（`src/kernel/tools/registry.ts:41`）：`name/parameters/execute/parallel/deferrable/
timeoutMs/descriptionText` + guard。只读/写分类按**工具名硬编码**在 policy（`src/policy/gate.ts:73-74` 的
`EDIT_CLASS_TOOLS`/`WRITE_CLASS_TOOLS`）——**插件工具无法声明自己的并发/风险需求**。

**调度原语缺失（已核实零命中）**：`grep -rn "schedul\|topolog\|parallelGroup\|concurren" src/kernel/tools/` = 空；
只有 `loop.ts:1218` 一把 `RwLock` + `:1223` `Promise.all`（无分组/无上限/无依赖）。
对照 zcode `tool/scheduler.ts:50`（拓扑排序→并行组→环检测，`DEFAULT_MAX_CONCURRENCY=10`）、
kimi `toolExecutor/toolScheduler.ts:17`（**资源冲突表**取代二值并行）、codex `tools/parallel.rs:141`（RwLock 读/写）。

### 3.3 专题三：会话与状态（"不重也不轻"——别乱动）

我方与 zcode/dsh 同属**事件溯源 sqlite + 闭集词汇表**阵营，且**机制纪律已对齐 dsh**
（`src/session/migrate.ts:1-19` 头注释直接引 dsh `session-format/src/chain.ts`）。
三点强于参考仓、**不要为了"轻"而拆掉**：
1. **31 类闭集事件 + C16 编译期穷尽互差为 never**（`src/kernel/events.ts:889-931`）——zcode/dsh 都没有这种闸门；
2. **C14 `assertJsonSafe` JSON 安全闸门**（`events.ts:41-92`）——参考仓无等价物；
3. **迁移链 fail-closed**（相邻缺失即拒 + 库比代码新拒开，`migrate.ts:254-267`）。

**真正的差异是"版本化层级"**：pi 把版本放**文档**上（`defineDoc` 带 version，旧值冷载重读，天然适合插件生态）；
dsh 放**格式**上（冻结迁移包 v0→v4）；我方放**库**上（单一 `user_version`）。
**后果**：我方插件**无法新增事件类型**（只有 `plugin` 一个泛型槽，`events.ts:676-679`），
想落自己的状态只能塞 `plugin.payload`——在"万物可插件"目标下是**扩展点缺口**（方案 W16/EP-8，可择机）。

## 5. "0 底座"定义与扩展点清单

### 5.1 内核必须保留（不可外置）

| 项 | 理由 | 现状 |
|---|---|---|
| 事件词汇表 + JSON 安全 + 闭集穷尽 | 一切投影/持久化/跨进程的公共语言；插件订阅面 | ✅ `src/kernel/events.ts`（零域依赖，正确） |
| 跨进程协议（agent-protocol / host protocol） | 进程边界的唯一契约 | ✅ `src/kernel/agent-protocol.ts`（缺版本号 → EP-9） |
| 进程模型（child 生命周期 + stdio） | "1 会话 1 child" 的底座 | ✅ `src/kernel/agent-child.ts`/`agent-process.ts` |

**依赖约束（建议写进 policy）**：

即把 `kernel.requires` 从 8 项压到 0~1 项，并置 `managed:true` 让它**硬失败**。
