## 1. 待确认的决策（阻塞项）

按 `AGENTS.md` §2，以下歧义**不默默选定**。每项列出解释与它影响的层。

### Q1. 部署形态
| 选项 | 含义 | 影响 |
|---|---|---|
| A. 纯本地单机 | agent 只跑在你自己机器的进程里，Web/IM 只是本地端口 | 沙箱可降 P2，多端同步可简化 |
| B. 服务器托管 | agent 跑在服务器，Web/IM 远程接入 | **沙箱必须 P0**，需认证与租户边界 |
| C. 混合 | 本地执行 + 远程接入 | 最复杂，需明确哪部分在哪 |

**这是最重要的一项。** 研究报告的核心推论"沙箱必须 P0"建立在"IM 消息可能来自非终端前的本人"之上 —— 若为 A 且 IM 只绑定你自己的账号，该推论减弱，沙箱可降级。

### Q2. 使用者范围
- A. 仅我自己 → 无需多租户、无需身份系统
- B. 小团队（<10 人）→ 需身份，但可共用一套策略
- C. 对外开放 → 需完整身份、配额、审计、滥用防护

影响：N 层（多端同步）、L 层（审计）、C 层（策略是否按人区分）。

### Q3. IM 平台优先级
- A. 飞书 —— `PiDeck/src/main/feishu/FeishuBridge.ts` 有现成参考
- B. Slack —— `opencode/packages/slack/` 有现成参考
- C. 其他（钉钉 / Telegram / 微信）

影响：仅 K 层实现顺序，不影响内核。**建议先做有参考实现的那个。**

### Q4. 桌面端
- A. 暂不做（符合你原话"以后桌面"）
- B. Electron（PI-Desktop / PiDeck 路线）
- C. Tauri（体积小，但需自行解决 host 通信）

影响：K 层。**建议 P2，不进 P0。**

### Q5. 模型来源
- A. API Key（实现最简单）
- B. OAuth 订阅制（需 `kimi-code/packages/oauth` 那样的独立包）
- C. 本地模型（需额外推理栈）

影响：J 层。A 与 B 可共存，但 B 必须在 P0 就确定，否则后期加会侵入内核。

### Q6. 并发会话写
一个会话是否可能被多端**同时**操作（如 Web 与 IM 同时发消息）？
- A. 否，同一时刻只有一个端能发 → N 层可简化
- B. 是 → 需要会话级锁与冲突解决

影响：N 层复杂度差异很大。

### Q7. 技术栈确认
研究报告建议**内核 TS + 沙箱/host 层 Rust 或系统原语**（依据：`pi-desktop` 自身就是这种混合，`codex` 全 Rust 是为做 bubblewrap 级沙箱）。你的团队技能是否支持？

## 2. 目标

做一个**可嵌入的多端 Agent 内核**，支持 Web + IM（+ 未来桌面）接入同一运行时，具备：

1. **可嵌入**：内核是库，不是发行版套壳
2. **可审计**：所有动作有轨迹、可回放、可追责
3. **可隔离**：危险操作有边界，不依赖"用户自己盯着"
4. **可恢复**：崩溃后能续跑，长任务不丢

## 3. 非目标（明确不做）

按 `AGENTS.md` §3（YAGNI），以下**明确排除**，避免为"未来可能用到"预埋：

| 不做 | 理由 |
|---|---|
| 自研模型 | 用现成 API |
| 自研协议替代 ACP | 用 ACP 适配（学 Grok `xai-acp-lib` 的独立包形态） |
| 多租户 / 计费 | Q2 未确认前不做 |
| 插件市场 | P2 之后再谈 |
| 复杂 UI 框架 | P0 不做任何 UI |
| 树状会话 | 先线性 + fork，树是 P1（Pi 的 `ForkCurrentStatePlan` 已预留抽象） |
| 自研沙箱 | 优先用系统原语（bubblewrap / Job Object / Seatbelt），不自造隔离 |

## 4. 核心场景

| # | 场景 | 验收要点 |
|---|---|---|
| S1 | 本地 CLI 发指令，agent 改代码 | 改前过策略、改后可回滚 |
| S2 | Web 上发起同一会话，看到同一进度 | 会话状态一致，不重复执行 |
| S3 | IM 里发"跑一下测试"，需审批时推回 IM | **审批能在 IM 端完成，不是只读通知** |
| S4 | agent 执行危险命令 | 默认拒绝或询问，且**无法绕过沙箱** |
| S5 | 长任务跑到一半进程被杀 | 重启后能续跑，不重复已完成的副作用 |
| S6 | 事后追查"谁让它删了那个文件" | 轨迹可回放，含发起端与审批人 |

S3 与 S5 是**多端 + 长任务的核心验收点**，也是最容易做假的地方（"推送到 IM"很容易，但**回来的审批要能唤醒原运行时**才是真的）。

## 5. 分层需求

优先级沿用研究报告：**P0 = 最小闭环，P0 跑通前不写任何 UI。**

| 层 | P0 需求 | P1 | P2 |
|---|---|---|---|
| A. Loop | 显式停止条件；steer 注入 | — | — |
| B. Tools | `read`/`write`/`edit`/`bash`/`glob`/`grep`；描述与代码分离 | 其余工具 | — |
| C. Policy | 三维求值＋默认 ask；待审批可跨端回转 | 权限预设 | — |
| D. Sandbox | 进程隔离 + 网络策略（**Q1 决定是否 P0**） | 容器后端 | 微 VM |
| E. Session | 事件源 + SQL；投影；fork | 树 | — |
| F. Context | overflow 与 compaction 分离 | 缓存优化 | — |
| G. Planning | — | Plan 模式 + goal 跨轮 | — |
| H. Subagents | — | task 工具 + 结算栅栏 | — |
| I. 扩展 | — | 内核 hooks/skills | 进程外插件 |
| J. Models | 单厂商可用 | 多厂商 | OAuth |
| K. Surfaces | CLI | ACP + Web | IM + 桌面 |
| L. Observability | 事件即轨迹 | 回放 | 审计报表 |
| M. 长任务 | — | 后台 job | 崩溃续跑 + idle 回收 |
| N. 多端同步 | — | 审批跨端 | 并发冲突解决 |

**P0 交付物 = A/B/C/E/F/J/K(仅 CLI)/L 的最小实现**，共 17 个文件（见 `04-module-map.md`）。
**D 层是否进 P0 取决于 Q1。**

## 6. 非功能需求

| 项 | 要求 | 验证方式 |
|---|---|---|
| 安全 | 工具**不能绕过沙箱**；默认 ask；密钥不入库 | 单测断言 `ToolContext` 无裸进程 API；`tools/license-audit.sh` |
| 可恢复 | 快照前必须 flush 事件 | 杀进程重启测试，断言无"快照说做了/事件说没做" |
| 可审计 | 每个动作可追溯到发起端与审批人 | 回放一条真实会话 |
| 可测试 | 内核可脱离 UI 单测 | loop 用假 provider 驱动 |
| 隐私 | 日志不含密钥、不含用户原文（除显式开启） | 日志脱敏断言 |

## 8. 验收标准（P0 完成定义）

1. 一个 CLI 会话能完整跑完 S1，事件落 SQL，重启后可 `fork` 出新分支
2. 危险命令（如 `rm -rf`）在无显式规则时**默认询问**，且规则可覆盖
3. 假 provider 驱动的 loop 单测通过，覆盖 continue/end 两条路径
4. 沙箱拦截一次越界文件访问（Q1=A 时可豁免）
5. `bash tools/license-audit.sh` 仍 16/16 通过

## 9. 风险

| 风险 | 缓解 |
|---|---|
| Q1 选错 → 沙箱做早了或做晚了 | **先答 Q1 再动 D 层** |
| 多端并发写导致会话状态错乱 | Q6 明确后再设计 N 层；P0 不开放多端写 |
| 抄了上游形状但没抄纪律（如 flush-before-snapshot） | 把纪律写成不变量 + 单测（见 `04-module-map.md` §不变量） |
| 上游演进导致报告过时 | 每轮开工前 `bash tools/snapshot.sh` + `git diff oss/SOURCES.lock` |
