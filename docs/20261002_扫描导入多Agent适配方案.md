> 用户指令：扫描导入适配更多 agent——去插件市场看 pi-desk 的"一体化会话导入"插件。
> 本报告 = 该插件的完整调研 + 我方 import-scan 的扩展方案（A~X 交用户裁决，打勾后实施）。
> 调研对象：PI-Desktop 官方插件市场 catalog（plugins.aiuo.net，48 插件）中的

## 0. 结论一句话

该插件的精髓不在"扫了六家"，而在**三驱动 + 声明式 spec 的适配架构**：所有工具的本地
会话存储收敛为三种磁盘形状（JSONL 对话转录 / SQLite session→message→part 三层 /
一文件一会话 JSON 树），每家的差异（角色路径、content 块、工具配对、注入剥离、时间单位）
全部表达为**纯数据 JSON spec**——新接一家 agent 是写配置，不是写代码。我方现有
import-scan 是三份手写适配器（且 OpenCode 源已过时：v1.x 已迁 SQLite），扩展=重做
为同款驱动架构 + 内置 spec 扩到六家 + 用户可自定义来源（声明式 JSON，纯数据校验）。

## 1. 该插件全景（实测解包）

**六内置来源**（README 权威表 + 源码核对）：

| 来源 | 数据位置 | 关键处理 |
| --- | --- | --- |
| ZCode | `~/.zcode/cli/db/db.sqlite` | node:sqlite **readOnly** 打开；过滤 `task_type='subagent_child'` 内部会话；按存储顺序还原工具调用 |
| WorkBuddy | `~/.workbuddy/projects/**/*.jsonl` | 剥 `<system-reminder>`/`<cb_summary>` 注入块；`function_call` 按 callId 配对；外置大结果回读；`ai-title` 优先 |
| Claude Code | `~/.claude/projects/**/*.jsonl` | 过滤 sidechain 与合成用户行（`<` 开头）；tool_use/tool_result 按 id 配对 |
| Codex | `~/.codex/sessions/**/*.jsonl` | 新旧两种格式兼容（unwrapPath 信封解包）；`# AGENTS.md` 等合成行过滤 |
| OpenCode | `%LOCALAPPDATA%\opencode\data\opencode.db`（Win）/ `~/.local/share/opencode/opencode.db`（XDG）——**多候选路径按序探测**（v0.4.9 修 Windows 找不到库的 #682） | SQLite v1.x 三层还原 |
| Pi | `~/.pi/agent/sessions/**/*.jsonl` | toolCall/toolResult 配对；`session_info.name` 优先 |

**三驱动抽象**（新 agent 的三类落点，内置六家全部落在其中）：

| driver | 磁盘形状 | 内置使用者 |
| --- | --- | --- |
| `jsonl-transcript` | 一行一条 JSON 记录的对话转录 | Claude Code、Codex、WorkBuddy、Pi |
| `sqlite-session` | SQLite：session→message→part 三层（或两层，正文在 message 行） | ZCode、OpenCode |
| `json-tree` | 一个 JSON 文件即一个会话 | 旧版 OpenCode / Claude 布局 |

**声明式 spec 能表达的所有差异**（docs/CUSTOM-SOURCES.md 全录，5196 行实现核对）：

- 角色/字段映射：`rolePath`/`roleMap`、`tsPath`/`tsUnit`、`content` 四种写法
  （字段路径 / 块数组挑 type 拼 text / first 依次尝试 / literal 常量）
- 条目过滤：`match {path, in}`（只处理 user/assistant）、`skipTypePath+skipTypes`
  （summary/system/sidechain）、`unwrapPath`（Codex `{timestamp,type,payload}` 信封——
  内层缺失自动退回原条目，新旧格式一份 spec 通吃）
- 注入剥离：`drop.startsWith` + `textOps`（`stripXmlBlocks`/`extractXmlTag`——纯字符串
  运算、标签名字符集校验，不是代码）
- 工具调用三种落地形状：A 条目级两阶段（function_call→function_call_result）/
  B 块级两阶段（assistant 的 tool_use 块 × user 的 tool_result 块按 id 配对）/
  C 单条目自带结果；`emitUnpaired`/`argsJson`/`errorValues`/`resultFormat`
- 外置大结果回读：`follow {marker, maxBytes}`——结果被截成"完整输出已存到 xxx"时读回
  落盘文件（**只在 spec 自己的数据根内**，越界保持原文本）
- 会话元数据：`idFrom`（filename/rule）+ `idFromEntry`（防 Codex 每个 response_item
  自带 id 被误当会话 id——两段查找）、`titleFrom: firstUser`、`projectFrom: parentDir`
- SQLite 特有：表/列名全映射、`sequence` 列探测排序（ZCode 有 OpenCode 无）、
  `session.exclude` 结构化过滤（绑定参数非拼 SQL）

**安全边界**（custom-sources.js 核对）：

- spec **只允许纯数据**：`eval`/`code`/`require`/`transform`/`script`/`__proto__`/
  `prototype`/`constructor` 等键**任意层级**直接拒绝；嵌套深度 ≤12
- 数据根目录拒绝 `/` 或整个 home；配置 ≤512KB、来源数 ≤25
- 资源上限：每来源 2000 文件 / 单文件 32MB（超限整跳）/ 20000 行（超限只读前 N 行）/
  单源扫描 90s 看门狗——错误配置不拖死面板；坏来源不中断其他来源
- SQLite 一律 readOnly 打开；导入走宿主 session.import 通道；幂等 id
  `import-<source>-<externalId>`

**增值功能"熔炉"（forge）**：导入后用宿主模型（宿主凭据与额度，插件不碰 key）把导入
会话蒸馏成项目约定与可复用做法，写回限工作区 `AGENTS.md`/`*.md`/`docs/**`/
`.agents/skills/**`。

## 2. 我方现状与差距

- 我方 `import-scan`（T-P3-150 A4 发现级）：三份**手写适配器**（claude/codex/opencode），
  cwd 归组+幂等+三计数——架构与该插件同源（当时即参考其主线 importers），但：
  1. **每加一家 agent 要写一份 TS 适配器**（该插件写一份 JSON spec）；
  2. **OpenCode 源已过时**：我方扫 XDG JSON 目录（旧版布局），v1.x 已迁 SQLite
     （`opencode.db`，Windows 在 %LOCALAPPDATA%）——Windows 用户实际扫不到；
  3. 无 ZCode 之外的 SQLite 驱动能力（无法接 Gemini CLI 类 SQLite 工具）；
  4. 无自定义来源机制（用户没法自己接小众工具）；
  5. 无资源上限（我方有 250 文件 codex 采样，但无每源看门狗/行数上限）。
- 可复用基建：幂等 id/三计数/cwd 归组/UI 勾选面板已与该插件同构（T-P3-150 落的）；
  SQLite 读取用已依赖的 better-sqlite3（readonly 打开）替代其 node:sqlite。

## 3. 改造方案（A~X，交用户裁决）

### P0（本轮核心）

- [ ] **A1 三驱动架构**：`src/host/import-drivers.ts`——`jsonl-transcript`/
  `sqlite-session`/`json-tree` 三驱动 TS 移植（spec → summaries 的 scan 面；spec
  解析用 getPath/extractText 同款纯函数）。SQLite 用 better-sqlite3 `readonly: true`。
- [ ] **A2 内置来源 spec 化**：claude/codex 两份手写适配器改写为内置声明式 spec
  （行为逐字等价——含 unwrapPath/注入过滤/tool 配对）；**opencode 源重写为
  sqlite-session spec**（多候选路径：%LOCALAPPDATA%\opencode\data\opencode.db →
  XDG_DATA_HOME → ~/.local/share/opencode，按序探测——修 Windows 扫不到的过时缺陷）。
- [ ] **A3 内置来源扩容**：新增 WorkBuddy、Pi 两家内置 spec（对齐该插件六家；ZCode
  就是我方本体不扫）；另加 **Gemini CLI**（`~/.gemini/tmp/*/` 会话 JSON——json-tree/
  jsonl 需实测落盘形状后定 spec）【形状未实测，实施时先采样再写 spec】。
- [ ] **A4 声明式自定义来源**：`docs/session-import-sources.json`（工作区，复用 fs.read
  边界？——我方 fs.read 边界是项目根白名单，工作区=activeProject 根 ✓）或
  `~/.aegent/import-sources.json`（全局，实施时定）；校验器照抄（FORBIDDEN_KEYS 任意
  层级+嵌套 12+根目录不许 home+512KB/25 来源）；UI 添加对话框扫描 tab 加"自定义来源"
  区（重新加载+错误显示+`自定义`徽标）。
- [ ] **A5 资源上限**：每来源 maxFiles 2000/maxBytes 32MB/maxLines 20000 + 单源 90s
  看门狗（对齐该插件；坏来源不中断——单源 try/catch 已有）。
- [ ] **A6 会话内容导入（A4b 提级）**：该插件的 convert 面证明内容导入可行且幂等
  （import-<source>-<externalId> 幂等 id + tool 配对还原）——把"发现级"升为
  **可勾选导入会话内容**：host 新 op `import-sessions`（勾选会话 → 驱动 convert →
  消息写入我方会话库（user/message+assistant/message+tool 事件流重建）→ 幂等跳过）。
  UI 扫描面板从"项目勾选"扩为"项目勾选+会话勾选（组全选/预览计数）"。

### P1（增强）

- [ ] **B2 蒸馏熔炉（记档后置）**：导入会话 → 辅助模型蒸馏项目约定写入 AGENTS.md
