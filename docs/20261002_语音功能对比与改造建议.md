## 0. 结论一句话

参考仓共同把"语音"做成了**四个域**：①听写输入（录音 UX + STT + 转写后处理）②朗读输出
（TTS + 流式播放）③音频传输（音频文件/工具结果直接进对话）④provider 管理（多协议、
key 零下放、SSRF 防护）。我方只有域①的最小链（点击录音→OpenAI 协议转写→填输入框），
**零朗读、零音频附件、单一 provider、设置页只有三行裸输入框**——"一个页面就一个功能"的
根源在此。参考仓最强处：qwen-code 的听写全链（hold/tap + VAD + 润色层 + 热词 + SSRF 防护
成套）、dsh 的本地离线识别（SenseVoice ONNX）与 Web 状态机/错误面、agentscope 的 TTS
中间件（边生成边朗读 + 流式 WAV 头 + 抢占式播放）、pi-desktop 的 TTS 管道与 key 零下放。
改造主体：录音体验三态化 + STT 多协议多 provider + TTS 朗读域 + 语音设置页分域重构 +
可选的音频附件与本地识别。

## 2. 我方现状与差距

现状基线（本会话逐文件核对）：

- **录音 UI**：`ui/app.js:978-1075`——🎤 点击开始/再点停止；MediaRecorder 缺省 webm 产
  blob→base64；转写文本**追加填入输入框**（补空格、不自动发送，app.js:1063-1068）；
  权限拒绝统一 warn 提示（app.js:1017-1019）；未配置点击后 toast 引导（app.js:996-998）。
- **转写链**：`ui/app.js:1046-1055` → op `stt-transcribe` → `src/host/speech-gateway.ts:20-44`
  （settings 读 baseUrl/model/language + credentials 库 "stt" 键解密）→
  `src/attachments/stt.ts:73-122`（OpenAI 协议 `POST {baseUrl}/audio/transcriptions`
  multipart，AUDIO_MEDIA_TYPES 三类白名单，错误零回显）。
- **设置面**：`ui/views/settings/agents.js:291-315` 语音【实验性】分节——三行裸输入框
  （STT 端点根/转写模型/语言提示）+ 一行 key 去向说明；settings 段
  `src/session/settings.ts:347-349`。
- **对照清单**：「语音【实验性】」行未勾（验收口径 = 三行能填能存）。

**与参考仓的差距清单**（每条都有参考先例，详见 §3/§5）：

1. 录音无任何视觉反馈：无计时、无波形/音量条、无转写中 spinner（对比 qwen-code
   录音 pill + dsh 80 根波形）。
2. 无自动停止：无时长上限、无 VAD 静音检测（对比 dsh maxDuration 自动 stop + qwen SoX
   静音检测）。
3. 无取消交互：录音中无取消按钮、Esc/失焦不回收（对比 dsh 取消矩阵 + pideck X 按钮）。
4. 无转写后润色（对比 qwen fast-model 润色层——我方 T-P3-146 一键润色基建可复用）。
5. 无热词/术语偏置（对比 qwen keyterms）。
6. 无插入冲突保护：转写返回时若用户已编辑草稿，直接追加可能错位（对比 pideck 前后缀
   映射 + dsh 修订号插入点）。
7. 单一协议：只支持 `/audio/transcriptions` multipart（对比 qwen chat `input_audio` 通
   道 + pi-desktop 双协议适配器——DashScope 等大厂 ASR 只走 chat 通道）。
8. 单一 provider 概念：无 provider 抽象（对比 dsh provider 注册表 location/languages
   元数据）。
9. 无 SSRF 防护：端点由用户自配，任意 URL 直接 fetch（对比 qwen https 强制 + 私网拦截 +
   DNS rebinding 校验）。
10. 错误不分型：权限/端点错/超时/空结果统一 warn（对比 pideck 错误码细分九文案）。
11. **零 TTS**：回复不能朗读（对比 pi-desktop /audio/speech 管道 + agentscope TTS 中间件
    + 流式播放）。
12. **零音频附件**：音频文件不能发模型、工具结果音频不能回灌（对比 opencode file part +
    kimi audio_url + MCP audio block）。
13. 设置页只有三行裸输入框，无模式/上限/测试/热词面。

## 4. 共同模式提炼

1. **录音三态/五态机是标配**：idle → recording（计时+电平反馈）→ transcribing（spinner）
   → 结果/失败。qwen/dsh/pideck 三家全部如此，我方只有 idle↔recording 两态无反馈。
2. **转写文本一律"插入供确认"，不自动发送**（qwen ChatEditor:3758 / dsh insertText /
   pideck 写回 draft）——我方行为与三家一致，保持。
3. **异步插入必须防冲突**：pideck 选区快照+前后缀映射、dsh 修订号插入点，两家殊途同归；
   我方目前直接追加，长录音+用户编辑场景会错位。
4. **STT 协议不止一种**：`/audio/transcriptions` multipart（OpenAI/whisper 系）与
   `chat/completions + input_audio`（DashScope/Qwen-ASR 系）两通道并存，多 provider 是
   实际需求不是过度设计。
5. **key 永不进渲染层**：pideck safeStorage+hasApiKey、pi-desktop getSecret+assertSameOrigin、
   我方 credentials 库 "stt" 键——三家一致，我方已达标。
6. **音频是瞬态数据**：dsh audio 瞬态原则（永不落 Session）、pideck "audio is never
   persisted"、pi-desktop 字节不过渲染层（scratch 路径进出）——隐私边界三家一致。
7. **安全护栏成套**：大小上限前置检查、请求超时、错误脱敏、失败冷却、SSRF 拦截——
   qwen 最全，我方目前只有 mediaType 白名单。
8. **TTS 是"语音"的另一半**：pi-desktop 管道完整、agentscope 中间件+流式播放成套；做朗
  读不需要实时语音对话那么重，`/audio/speech` 整段合成即可起步。
9. **能力位门控 + 降级文案**：模型不支持音频时改写为给模型的说明文本（opencode/kimi），
   而非硬报错。
10. **本地识别可后置**：dsh SenseVoice 是完整蓝本但工程量大（模型下载/子进程/队列）；
    OpenAI 兼容 API（含自建 whisper.cpp/LocalAI 网关）已覆盖绝大多数场景——pi-desktop
    规格也把本地模型归到"OpenAI 兼容服务器"一类。
