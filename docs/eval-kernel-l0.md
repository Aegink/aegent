# L0 内核自研评估

> 触发问题：*"我感觉 pi 是最适合内核的，我们是不是也可以做一个最基础的（就是 0 这个最核心的），先评估。"*
> 本文只做评估，不含实现。所有数字均为本机实测（`oss/SOURCES.lock` 锁定 commit），非记忆。

---

## 0. 结论先行

| 问题 | 结论 |
| --- | --- |
| L0 内核能自研吗？ | **能，且规模可控** —— 自研 L0 ≈ **1,900–2,500 行** |
| 凭什么说可控？ | pi 自己的简单核心就是 **2,007 行**（实测），同量级 |
| 哪一层**不该**自研？ | **模型层**（pi-ai 实测 **25,141 行 / 183 文件 / ~80 provider**）—— 自研是数月无差异劳动 |
| 最大风险是什么？ | **不是 loop 写不出来，是 L0 的事件词汇表定小了**（见 §6） |
| 建议 | **自研 L0 + 依赖 pi-ai 作模型层**；不依赖 pi-agent-core 的 loop，但**精读它的 session 层**（见 §8） |

---

## 1. 先澄清一处歧义

"做一个最基础的"有两种读法，工作量差一个数量级：

- **(A) 自研最小内核** —— pi 只作设计参照，代码自己写。产出约 2 千行。
- **(B) 依赖 pi 的包** —— 直接把 `@earendil-works/pi-agent-core` 当依赖，只写上面那一薄层。产出约数百行。

两者不是二选一。本文的结论是**按部件混合**：loop / 词汇表 / 策略 / 沙箱自研（A），模型层依赖（B）。理由逐条见 §4、§5。

**若你的原意是 (B) 整体依赖**，那要看 §7 的三条代价能不能接受 —— 其中"词汇表不再由我们定义"与 Q9（封闭联合）直接冲突。

---

## 2. L0 的精确边界

**L0 = 单进程内跑完"用户发话 → 模型回话 → 调工具（过策略）→ 结果回灌 → 落盘 → 可恢复"。**

不含：多端、子代理、goal、插件、压缩策略之外的上下文工程、UI。

对应需求文档 P0 中 A/B/C/D/E/F/J 六层的条目：A7、A9、B10、B11、B12、C10、C14、C15、C16、D15、E11、E12、E13、F9、F10、J4。

---

## 3. 关键证据：pi 自己把"内核"分成了三层

`oss/pi/packages/agent` 实测 **33,539 行**。但这个数字**不是内核规模**，它内部是分层堆叠的：

| 层 | 行数 | 文件 | 说明 |
| --- | ---: | ---: | --- |
| **简单核心** `agent.ts` + `agent-loop.ts` + `types.ts` | **2,007** | 3 | **不 import 任何 `harness/`** —— 已实测验证 |
| harness 顶层 12 文件 | 3,548 | 12 | system-prompt / hooks / skills / telemetry / context |
| `harness/session` | 7,108 | 29 | 持久化、lane、checkpoint、inbox、fork、JSONL、v3 迁移 |
| `harness/runtime` | 7,473 | 21 | drive / lane(2,012) / reducer |
| `harness/pico3` | 8,100 | 25 | **实验层**，导出路径即 `./experimental/pico3` |
| `harness/tools` + `compaction` + `env` + `utils` | 3,874 | 17 | 工具实现、压缩、node 环境适配 |
| 其余（`proxy.ts` / `index.ts` / `search`） | 1,429 | — | |

**读法**：pi 的"内核"是 **2 千行**，33k 是它长出来的**产品级 apparatus**。
我们自研 L0 要对标的是那 2 千行，不是 33k。

其中 `pico3` 被官方标记为 experimental —— 说明**连 pi 作者自己都还在重写这一层**。我们此时去整体依赖它，等于把地基押在一个在建的楼层上。

## 4. 按部件拆分：该自研 vs 该依赖

| 部件 | 我方 L0 估算 | 建议 | 理由 |
| --- | ---: | --- | --- |
| 事件词汇表 | ~120 | **自研** | Q9 封闭联合，这是我们的主语，不能由别人定义 |
| loop（turn 边界 / 停止决策 / 工具批） | ~400 | **自研** | 核心差异点；pi 的 898 行含大量 P1 才需要的东西 |
| 工具注册表 + `read`/`write`/`bash` | ~450 | **自研** | 必须与 B12 输出契约、C 层策略咬合 |
| 策略求值 `findLast` 三点 | ~80 | **自研** | 60 行，抄形状即可（OpenCode） |
| 会话 append / project | ~350 | **自研（极简版）** | pi 的 7,108 行是成熟版；L0 只要 append + 顺序重放 |
| 沙箱 exec | ~250 | **自研** | Windows 是我们的差异点，不是 pi 的强项 |
| 压缩（turn 边界） | ~200 | **自研** | F9 的落点只有几十行判断，难在时机不在代码 |
| **模型层（provider / 协议 / 流 / OAuth）** | **0** | **依赖** | **见 §5** |
| **合计自研** | **~1,850–2,500** | | |

与 pi 简单核心 2,007 行同量级 —— 这是"能自研"最有力的证据：**不是我们乐观，是这条路已经有人走通且留下了尺寸记录。**

## 5. 最大陷阱：模型层绝不能自研

`oss/pi/packages/ai` 实测 **25,141 行 / 183 文件**，其中：

| 文件 | 行数 |
| --- | ---: |
| `api/openai-completions.ts` | 1,726 |
| `api/openai-codex-responses.ts` | 1,666 |
| `api/anthropic-messages.ts` | 1,520 |
| `api/bedrock-converse-stream.ts` | 1,344 |
| `api/mistral-conversations.ts` | 946 |
| `api/openai-responses-shared.ts` | 793 |
| `api/google-*`（3 文件） | 1,538 |
| `auth/oauth/*`（3 文件） | 1,454 |

再加约 80 个 provider 的型号表。

**这 25k 行里没有一行是我们的产品差异。** 全部是"让各家 API 说同一种话"的转换劳动。
自己写，哪怕只支持 3 家、只做流式 + 工具调用 + usage + 错误处理，也要 **3,000–5,000 行**，
且**永远追不上上游**：上游每加一个 provider、每改一次协议，都要重做一遍。

**判断：模型层是 L0 的边界，不是 L0 的内容。** 这是整个评估里最省时间的一条。

## 6. L0 的真实风险不是 loop，是词汇表

Loop 不难写。**难的是词汇表是一次性单向门。**

Q9 已定**封闭联合**，配 C16（新增事件类型必须同步 `assertNever`）。这意味着：
**L0 定下的事件类型集合，就是此后所有插件、所有持久化、所有投影的边界。**
定小了，后期扩张的代价就是 `dsh/rejected/architecture/2026-06-16-typed-event-schemas.md` 里那个悬崖 —— **全仓词汇表重构**。

**实测发现的缺陷**：`docs/research/04-module-map.md` 的词汇表草稿只有 **10 个事件类型**，
但 P0 需求里至少有 **3 项没有对应事件**：

| 缺失事件 | 由哪条 P0 需求要求 | 现状 |
| --- | --- | --- |
| **取消 / 中断的终态**（带 cause） | **A7**（P0） | 草稿的 `turn_end` 无终止原因字段，无法区分"正常结束"与"被中断" |
| **代码状态检查点** | **E11**（P0） | 完全缺失；S1 的 revert 依赖它 |
| **压缩记录** | **F9 / F11**（P0/P1） | 完全缺失；压缩后必须留下可回放的记录 |

外加两处**形状**约束未落进草稿：C14（事件不得含 runtime 对象）、E12（整值事件，非裸 delta）。

**结论**：L0 的第一份产物不是 `loop.ts`，而是**先把词汇表定到能覆盖未来三类扩展**（取消、检查点、压缩）。
这件事只能现在做，做完就便宜了。

## 7. 依赖可行性：已验证，不是推测

| 检查项 | 实测结果 |
| --- | --- |
| `@earendil-works/pi-ai` 是否发布 | **是**，`npm view` 得 `0.87.1`，`license = MIT` |
| `@earendil-works/pi-agent-core` 是否发布 | **是**，`0.87.1`，MIT |
| 是否有 Node 版本包袱 | 有 `legacy-node20` dist-tag（`0.74.2`）—— 说明维护了 Node 20 分支 |
| 本机 Node | **v22.19.0**，满足其 `engines: >=22.19.0` |
| J4 模型身份二元组能否满足 | **能** —— `Model` 接口原生含 `provider: ProviderId` + id |
| 换模所需的注册表 API | `getModel(provider, id)` / `getModels(provider?)` / `setProvider` 齐备 |

**若走整体依赖 (B)，代价是三条**：
1. **词汇表不再由我们定义** —— 与 Q9 封闭联合的初衷冲突（虽然 pi 也是封闭联合，但那是**它的**联合）
2. 继承 `harness/runtime` 的 lane / inbox / checkpoint 模型 —— 那是它为自己的产品选的，我们没选过
3. 上游是**单一维护者**的项目，且 `pico3` 自标 experimental，重写正在进行中

## 8. 建议

1. **L0 自研，模型层依赖 pi-ai。** 自研规模 ~2 千行，有同量级先例。
2. **L0 的第一个产物是事件词汇表，不是 loop。** 先补齐 §6 的三类缺失事件，再动 `loop.ts`。
3. **不整体依赖 pi-agent-core，但要精读它的 `harness/session`。**
   我们 L0 不需要它的 lane / inbox / checkpoint，但 **A9（turn 只能入队）** 与
   `TerminalStatus = "completed" | "declined" | "aborted" | "failed"` 这些**词汇选择**
   会决定我们的词汇表有没有留对位置。**读它的类型定义，不依赖它的运行时。**
4. 先修 `04-module-map.md` 的词汇表草稿（§6 三项），再更新 `requirements.md`。
