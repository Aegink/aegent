## 0. 结论一句话

参考仓的"0 底座"不是"最小行数"，而是**最小语义面 + 装配全外置**：

- **pi 把内核压到极限**：`packages/agent` 只有 6 文件 2,519 行（agent 循环 + 类型 + 流函数），
  依赖只有 `pi-ai` + `typebox`；连 `/mcp`、codemode、tool-search 都是**与第三方同一接口的内置扩展**
  （`extensions/index.ts:6-13`，`replaceable: true`）。
- **dsh 把"装配"外置到 YAML**：331 个子包、每个工具一个 npm 包，默认组合写在
  `packages/bundle/base/cordis.patch.yml`（94 行 insert、517 行）；内核只提供 Service 仓库与生命周期。
- **pi-desktop 用"上游内核 + 本地薄运行时"**：内核是别人的 `pi-ai`/`pi-agent-core`（ADR 0002），
  自己只写 `agent-host`(2.5K, 无传输语义核) + `host-runtime`(6.1K, 无 Electron 运行时) + Rust host-core(80K)。
- **zcode/codex 是"重内核"对照组**：codex `core` 单 crate 250,171 行 / 583 文件、~60 条仓内依赖；
  zcode 靠 `architecture-policy.yaml`（400 行/文件、禁环、禁深导入、分层序）事后治理，而非内核瘦身。
- **我方**：`src/kernel` 21,978 行 / 82 文件，且 kernel 直接声明依赖 8 个域
  （`architecture-policy.json` kernel.requires）+ 未声明的 scheduler——**这是"装配中心"而不是"骨架"**。
  全仓架构检查当前 1 error / 42 warning，且 kernel 是依赖环上节点却 `managed:false`（只 warn）。

### 2.3 每仓结论

- **zcode = 治理最完整**：`requires` + `publicEntrypoints` + `layers/layerOrder` + `forbidCycles/forbidDeepImports` +
  `maxFileLines/maxContractLines/maxPublicMethods` + baseline 渐进采用 + `architecture:context <module>` 给 agent 读的上下文。
  这套策略与我方 `architecture-policy.json` + `tools/architecture-check.mjs` 是**同源设计**（我方头注自述"渐进采用（zcode 同语义）"）。
- **pi = 治理最"经济"**：不查环，查"入口图的代价"——"importing a 1-file pure function through a barrel costs ~37 MB
  of evaluated module graph"（`check-entry-graphs.mjs:6`）。这是**为 0 底座服务的治理**：入口预算就是内核瘦身的护栏。
- **dsh = 治理最"分布"**：没有中心化方向规则，靠 331 个包的独立发布 + `check-workspace-constraints` 兜底；
  依赖方向由 cordis `inject` 在**运行时**决定（服务可用性驱动装载），编译期不表达。
- **pi-desktop = 治理"防回潮"**：不追求瘦内核，追求"facade 不变成第二实现"+ 文件大小棘轮。
- **opencode = 治理最弱**：方向规则只有文档，没有 gate。
- **codex = 治理"交给编译器"**：155 crate 的依赖图由 Cargo 强制无环，但 core 自身 250K 行无人管。

### 3.3 关键锚点摘录

**pi-desktop 隔离 ADR（进程级隔离的代价与边界）**：
```

- 每插件 utilityProcess.fork，最小环境（PATH/HOME/PI_PLUGIN_ID/NODE_ENV），
```

（`oss/pi-desktop/docs/adr/0008-plugin-runtime-isolation-target.md`）

### 4.1 三个"0 内置"范式的证据

**(a) dsh：装配即数据（最强"万物可插件"）**
```yaml
# oss/deepseek-harness/packages/bundle/base/cordis.patch.yml:1-6
# The dsh-base bundle patch: the shared core of each base-backed profile...
# Row order carries no load semantics (activation is service-availability driven)
- insert:
    - id: tool-bash
      name: '@deepseek-ai/dsh-tool-bash'
    - id: tool-fs
      name: '@deepseek-ai/dsh-tool-fs'
```
94 行 insert / 517 行；每个工具、每个 UI 面板、每个模型适配器都是一行 YAML + 一个独立包。
**"0 内置"的极限形态：内核只是 Service 仓库，默认组合是一份可被用户 patch 覆盖的数据。**

**(b) pi：内置 = 可替换的扩展**
```ts
// oss/pi/packages/coding-agent/src/extensions/index.ts:6-13
export const builtInExtensions: InlineExtension[] = [
	{ name: "llama.cpp", factory: llamaExtension, builtin: true },
	// Replaceable: an extension that registers `codemode`, `tool_search`, or `/mcp` (such as a third-party
	// MCP extension) takes over instead of running alongside the built-in one.
	{ name: "codemode", factory: codemodeExtension, replaceable: true, builtin: true },
	{ name: "tool-search", factory: toolSearchExtension, replaceable: true, builtin: true },
	{ name: "mcp", factory: mcpExtension, replaceable: true, builtin: true },
];
```
——内置项与第三方项**同一数组、同一接口**，还显式声明可被第三方"接管"。这是"0 特权内置"的最干净表达。

**(c) pi-desktop：捆绑插件走公共通道**
```md
ADR 0105（→ 被 0241 取代，理由继承）：
"`pi.files` is a first-party plugin shipped from apps/desktop/resources/plugins/
 and contributes its view through `contributes.views` just like a third-party plugin."
"Give the bundled plugin private host capabilities: Rejected: a private channel
 would not test the public plugin API"
```
`apps/desktop/resources/plugins/` 实际有 `pi.browser`、`pi.file-manager` 两个捆绑插件（可停用不可卸载）。

### 4.2 反例：编进内核的形态

- **codex core**：agent/多代理/guardian/compact/exec_policy/context_manager 全在 `core`（250K 行）。
  其"插件"只到"声明式资源包（skills/MCP/hooks）"层——**运行期贡献面极窄**，所以 core 必须自己扛。
- **opencode core**：32,993 行，`packages/core/package.json` 的 exports 甚至允许 `"./*": "./src/*.ts"`
  （**任意深导入**）——架构边界几乎不存在。

## 6. 我方扩展点缺口清单

> 目标：让 40 个内置工具 / IM 渠道 / scheduler / lsp / mcp / sandbox 可**外置**。
> 每项给"内核需保留的接口与生命周期"+"现在缺什么"。

### 6.1 工具外置（40 个 builtin）

**内核必须保留**：
1. `ToolDef` 契约——已有且质量高（`src/kernel/tools/registry.ts:41-110`：execute(args, ctx)、parallel、
   deferrable、timeoutMs、descriptionText）。**保持不动**，这是最该保留的接口。
2. `ToolRegistry` 注册/注销——已有（`:182` / `:194`）。
3. `ToolContext`（ctx.env 能力面，D4 红线：进程能力只在实现层）——已有（`src/kernel/tools/context.ts`）。
4. 工具**描述来源**（B2：`descriptions/<name>.txt` 与代码分离）——已有（`registry.ts:9-11`），
   插件工具走 `descriptionText` 内联（`registry.ts:100-105`）。
**现在缺什么**：
- **缺"工具来源"抽象**：内置工具由 `registerBuiltinTools(registry, options)` 一次性注册
  （`builtin/index.ts:100`），options 是 20+ 字段硬编码依赖表。外置需要把每个工具变成
  `{ name, factory(deps), 依赖声明 }` 的可枚举条目，由装配按依赖可用性条件注册。
- **缺"工具贡献的贡献者身份"**：现在工具来源只有 builtin 与 plugin（`<插件名>__<工具名>`）。
  外置后需要第三种来源（"内置包"）与插件同通道，参照 pi 的 `replaceable: true`（pi 内置扩展可被第三方接管）。
- **缺 BUILTIN_TOOL_NAMES 的单一事实源**：`:67` 手写清单与 `:100` 注册清单双份。
  外置后应由工具包清单生成（pi 的 `check-entry-graphs` 式"清单即事实"）。

### 6.2 渠道外置（IM）

**内核必须保留**：
1. `ImSurface` 接口——已有且干净（`src/host/im-surface.ts:20`：handleWebhook / deliverEvent + surfaceId）。
2. **审批回传通道**（`parseApprovalCommand`，`:51`）+ 租约面（`withLease`，`:59`）。
3. host webhook 路由分型（`src/host/server.ts` 按路径转发）。

**现在缺什么**：
- **缺"渠道注册表"**：两实现是硬编码装配，插件无法新增渠道。需要 `registerChannel(surfaceId, factory)`
  + 渠道声明进 manifest（contributes.channels，参照 pi-desktop `contributes` 的同类项）。
- **缺渠道凭据的插件供给面**：现在凭据走环境变量注入（`im-surface.ts:8`）；
  外置后需要"插件设置 → 渠道凭据"的注入契约（我方已有 contributes.settings，缺 channel 绑定）。
- **缺 IM 出站的宿主事件契约**：`deliverEvent(event: JsonRecord)` 是裸 JSON——需要收紧为
  "事件摘要投影"（哪些事件可外发、脱敏规则），否则渠道插件能看全量事件流。

### 6.3 scheduler 外置

**内核必须保留**：
1. `SchedulerRuntime` 接口——已有（`src/host/scheduler-ops.ts:24`：store/scheduler/jobs/tickOnce/stop）。
2. 定时投递通道（`sendPrompt`，`:42`）+ host-owned 授权语义（`:8-12` 记档）。

**现在缺什么**：
- **缺调度器注册面**：`createSchedulerRuntime` 是 host 内单例（`:50`）。外置需要
  `registerScheduler(kind, factory)` + 任务定义 schema 贡献（cron 只是 kind 之一）。
- **缺"任务来源"抽象**：off-peak/webhook 已记档为"装配缺口"（`scheduler-ops.ts:14`）。
  外置需要一个统一的"任务来源"接口，让 cron/offpeak/webhook/插件自定义来源同轨。
- **缺 kernel 侧的解耦**：`src/kernel/agent-process.ts:69-72` 直接 import scheduler 的
  browser/computer 工具——这是 kernel 依赖 scheduler 的实证，外置前必须先断开。

### 6.4 lsp 外置

**内核必须保留**：
1. `LspTransport` + `LspClient` 接口——已有（`src/lsp/client.ts:68` / `:142`）。
2. 工具面的 `lspClientFor` 注入点——已有（`builtin/index.ts:179`）。

**现在缺什么**：
- **缺 server 解析的注册面**：`lspClientFor` 由装配硬注入。外置需要
  `registerLspServer(matcher, factory)`（按文件路径/语言匹配），并允许插件声明 `contributes.lspServers`。
- **缺 lsp 域的自洽**：`src/lsp/` 只有 240 行（client.ts 一个文件），域内没有
  server 生命周期（启动/健康/重启）——外置后这些必须由 host 提供（对照 dsh `packages/lsp` 独立包）。

### 6.5 mcp 外置

**内核必须保留**：
1. MCP 客户端 + 工具桥（`src/mcp/registry-bridge.ts`：`McpConnection`，工具名 `<server>__<tool>`）——已有。
2. 插件 SDK 的宿主面（`src/mcp/plugin-sdk.ts`）。

**现在缺什么**：
- **缺"mcp 域不依赖 host"**：`src/mcp/ws-plugin.ts:24` import `../host/protocol.js` 是反向依赖；
  MCP 是协议适配器，不该知道 host 的协议版本。需把 PROTOCOL_VERSION 下沉到 kernel/protocol。- **缺 MCP server 的插件贡献落点**：contributes.mcpServers 已声明（`plugin-manifest-contributes.ts:119`），
  但装载后谁启动/谁注入 env/谁做命名空间，散在 loader 与装配里——需要统一的 "MCP server 供给者" 接口。

### 6.6 sandbox 外置

**内核必须保留**：
1. `SandboxBackend` 接口——已有且是全仓最标准的端口形状（`src/sandbox/backend.ts:66-74`：
   supportedModes + spawn，fail-closed 抛 SandboxUnavailableError）。
2. 模式语义 + 升级审批通道（`bashSandbox.approvals`，`builtin/index.ts:172-178`）。

**现在缺什么**：
- **缺后端注册面**：`createRoutingBackend` 在 assembly 里硬选（`src/kernel/assembly.ts:47-53` import）。
  外置需要 `registerSandboxBackend(mode → factory)`，且 kernel 不得直接 import sandbox 实现
  （现在 `src/kernel/assembly.ts` 直接 import `../sandbox/containment.js`）。
- **缺 sandbox 域的 kernel 依赖倒置**：sandbox 依赖 `kernel/tools/env.js`（ExecutionEnv）——
  这是合理的（端口在 kernel），但 kernel 又 import sandbox（`assembly.ts`）→ 环。
  正确方向：kernel 只出接口，装配层（host 或独立 assembly 包）做绑定。

### 6.7 缺口的共同根因（一句话）

**我方所有域的"端口"都已存在且质量高（SandboxBackend / ImSurface / SchedulerRuntime /
LspClient / McpConnection / ToolDef / EVENT_TYPES），但"注册面"全缺**——
端口是"实现替换"，注册是"运行期增删"。目前所有绑定都发生在**装配期**的
`createChildAssembly` + `registerBuiltinTools` + `loadConfiguredPlugins` 三处硬编码，
所以"外置"等价于"改装配代码"，而不是"装一个包"。

## 7. "0 底座"最小集建议

### 7.1 内核必须保留（不可外置）

| 项 | 理由 | 依赖约束 |
|---|---|---|
| 事件词汇表 + JSON 安全 | 一切投影/持久化/跨进程的公共语言；插件订阅面 | 零域依赖（现状正确） |
| 跨进程协议（agent-protocol / host protocol） | 进程边界的唯一契约 | 零域依赖 |
| 进程模型（child 生命周期 + stdio） | "1 会话 1 child" 的底座 | 只依赖协议 + logger |
| 链式中间件（chain/hooks） | 权限/压缩/预算的挂载骨架 | 零域依赖 |
| agent 循环（loop.ts） | 基本原语之一 | 只依赖：事件 + store 接口 + provider 接口 + ToolDef 接口 |
| 会话事件源（store 接口 + 事件投影） | 基本原语之二 | 只依赖事件词汇表 |
| 工具契约（ToolDef + ToolRegistry + ToolContext） | 派生原语的注册面 | 零域依赖 |
| 预算/deadline/队列/运行态 | 循环的无状态配件 | 零域依赖 |
| 插件 manifest 校验 + 装载协议（SDK 形状） | 万物可插件的入口 | 只依赖事件词汇表 |

**目标规模估计**：把 assembly/agent-process/agent-protocol/events/loop 中
"域装配"部分剥离后，内核可压到 ~8,000 行（现在 21,978），接近 pi-desktop 的
"语义核 2.5K + 运行时 6.1K" 量级。

### 7.2 必须外置（从 kernel 移出）

| 现位置 | 应去处 | 理由 |
|---|---|---|
| `kernel/tools/builtin/**`（39 文件） | 独立工具包（每工具或每族一包） | 工具是派生原语，非骨架 |
| `kernel/assembly.ts`（1,360） | `src/assembly/`（装配层，非内核） | 装配是"把域接起来"，属二/三层 |
| `kernel/agent-process.ts`（2,033） | 拆：进程编排留 kernel，域装配移 assembly | 现在它同时是进程入口与装配中心 |
| `kernel/subagent.ts`（642） | `src/subagent/` 域包 | 子代理是派生原语 |
| `kernel/prompts.ts`（388）/`skills.ts`（259） | `src/prompts/` / 已有 skills 域 | 内容域，非骨架 |
| `kernel/model-switch.ts` / `plan-mode.ts` / `goal.ts` | 各自域包 | 会话策略，非骨架 |
| kernel 对 scheduler/sandbox/mcp/lsp 的 import | 全部改为"装配层注入接口" | 断开 §5.5 的环 |

### 7.3 内核的依赖约束（建议写进 policy）

```
kernel 只允许依赖：kernel/* + models/provider 接口 + session/store 接口 + 事件词汇
kernel 禁止依赖：scheduler / sandbox / mcp / lsp / context / policy / attachments 的任何实现
（这些域可以提供"接口文件"，但接口必须住在 kernel 或被 kernel 拥有的 contracts 里）
```
——即把 `architecture-policy.json` 的 `kernel.requires` 从 8 项压到 0~1 项，
并置 `managed: true` 让它**硬失败**。

### 7.4 最小集之外：需要新建的"注册面"（不是新能力，是新的绑定方式）

1. `registerToolProvider(source, factory)` —— 工具来源可枚举（内置包/插件/动态）
2. `registerChannel(surfaceId, factory)` —— IM 渠道
3. `registerSandboxBackend(mode, factory)` —— 沙箱后端
4. `registerScheduler(kind, factory)` —— 调度器种类 + 任务来源
5. `registerLspServer(matcher, factory)` —— LSP server
6. `registerMcpServerProvider(provider)` —— MCP server 供给者
7. 插件 SDK 能力面从 2 项扩到"按域分片"（net/fs/session/provider/service/bus）
8. 插件常驻服务 + 插件消息总线（对照 pi-desktop ADR 0040）

## 8. 候选方案（供裁决）

> 代号 A1~A9。成本：小=单文件/单模块；中=多文件+测试；大=跨域重构+回归。
> 每项给：做什么 / 成本 / 风险 / 依赖。

| 代号 | 做什么 | 成本 | 风险 | 依赖 |
|---|---|---|---|---|
| **A1** | **kernel 归零治理**：把 `kernel.requires` 压到 0，`managed:true` 硬失败；先断 kernel→scheduler（`agent-process.ts:69-72`）与 kernel→sandbox（`assembly.ts:47-53`）两条边 | 中 | 装配面要重新找家（assembly 移出 kernel）；测试大改 | 无 |
| **A2** | **拆 assembly 出 kernel**：`src/kernel/assembly.ts`(1,360) + `agent-process.ts` 的装配段 → `src/assembly/`（managed:true，只允许单向依赖 kernel + 各域接口） | 中 | 行数上限会逼拆分；`agent-process.ts` 2033 行需要先拆 | A1 |
| **A3** | **工具外置试点**：把 5 个纯函数工具（`current-time`/`ls`/`glob`/`grep`/`read`）改成"工具包"形态（`ToolProvider` 接口 + 清单生成），验证外置通道 | 小 | 低（纯函数工具无域依赖） | 无 |
| **A4** | **BUILTIN_TOOL_NAMES 单一事实源**：由注册清单生成，消除 `builtin/index.ts:67` 与 `:100` 双份 | 小 | 低 | A3 可顺带 |
| **A5** | **插件 SDK 能力面分片**：从 `{registerTool, subscribe}` 扩到 `{net, fs.read, session.read, settings, bus}`，按 manifest.capabilities 声明授予；token 仍不泄内核句柄 | 中 | 能力面扩大=攻击面扩大；需保持"声明未实现即拒装"的 fail-closed | 无 |
| **A6** | **插件常驻服务 + 消息总线**：加 `contributes.services`（≤N/插件，broker 管 start/stop/重启）+ 声明式 topic 总线（限流） | 中 | 需要 host 侧 supervisor；对照 pi-desktop ADR 0040 的 caps 与退避 | A5 |
| **A7** | **域注册面（6 个 register*）**：工具来源/渠道/沙箱后端/调度器/LSP/MCP 供给者，统一"装配层绑定接口" | 大 | 每域都要动装配与测试；需先有 A2 的装配层 | A1+A2 |
| **A8** | **provider 贡献**：允许插件声明模型供应商（contributes.providers，含 oauth 回调） | 中 | 供应商是敏感面（凭据）；需沿用 trust 分轨 + 审批 | A5 |
| **A9** | **依赖治理收紧**：kernel 环硬失败；补 `publicEntrypoints`（至少 kernel/session/models 三域）激活 forbidDeepImports；修 1 error（`protocol-settings.ts` 403 行） | 小 | 存量 warning 需要 baseline（zcode 同款渐进） | 无（可立即做） |

**建议顺序**：A9（立即，零风险）→ A1+A2（底座归位）→ A3+A4（工具外置试点）→ A5 → A7 → A6/A8。
