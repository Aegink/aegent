# 壳层复用评估报告：能否拿参考仓的壳子套我们的内核（2026-10-13）

> 问题：自研 UI（壳）成本高，能否直接复用 oss/ 参考仓的壳接到 aegent 内核上？
> 方法：逐仓盘点 UI 形态/技术栈/规模/与 agent 核心的接缝/移植必须重写的层（带
> file 锚点），与我们的内核接缝（WS 四信封协议）和 UI 现状（原生 JS 23,066 行）对比。

---

## 一、结论（先说答案）

**"直接拿壳套内核"对绝大多数参考仓不成立**——参考仓的 UI 不是可插拔的独立层，
而是与其自身后端数据模型（事件类型、会话模型、服务 descriptor）深度耦合的
投影层。换后端 = 重写该层，而重写量往往超过自研。

**但有三个真实可行的落点**：

| 路线 | 做法 | 适用 | 成本量级 |
|---|---|---|---|
| **A. 不换壳换打法**（推荐用于 Web/桌面） | 引入轻量组件方案（preact/htm 或 lit，保持零/极简构建）重写交互层，把 23k 行手写 DOM 收敛为组件 | 解决"手写难"的根因 | 中（渐进，可分期） |
| **B. 拿 pi-tui 加终端形态**（推荐用于快速见效） | pi-tui 是 MIT 独立渲染库（46 文件/19.5k 行，**无 agent 依赖**）——写"四信封→Component"适配即可获得 TUI 前端 | 接受终端形态 | 低（适配约 1~2k 行） |
| **C. 借架构不借码** | 抄 opencode 的 HTTP+SSE / codex app-server 的 req/notif/resp 协议设计细节，改进我们的 WS 协议 | 协议演进 | 极低（设计参考） |

**明确不建议**：摘 zcode / qwen web-shell / opencode app 的完整 Web 壳（体量
1492~1023 文件、绑各自服务层）；摘 Rust TUI（grok/codex，语言+编译期耦合）；
摘 pi-desktop（LGPL + Electron 87k 行）；cc-switch（不是会话 UI，是配置管理器）。

## 二、事实对照

### 2.1 我们的接缝与壳现状

- **内核接缝**：WS 四信封（hello / request / response / event）+ sessionId 一级
  路由；33 事件闭集；子进程 1 会话 1 child。**已经是"壳与内核分离进程"的形态**
  （host 进程 + agent-child）。
- **UI 现状**：`ui/` 55 文件 / **23,066 行**（不含 vendor），原生 JS 无框架手写 DOM，
  零构建（静态文件直发）；已实现对话流/审批/设置/文件树/评审/浏览器面板等全套交互。
- **对比**：我们的壳比参考仓小 **3~25 倍**（见下表）——"手写难"的感受来自
  在零框架约束下手工完成同等交互量，而非壳本身过大。

### 2.2 参考仓壳盘点（关键列）

| 仓 | UI 形态 | 技术栈 | UI 规模（文件/行） | 与后端接缝 | 移植必须重写 | 许可 |
|---|---|---|---|---|---|---|
| pi | TUI 应用 + **独立渲染库** | TS，无框架 | 库 46/19.5k；应用 UI 62/21.9k | 同进程 `session.subscribe`；另有 CBOR 帧 | 应用层须重写；**库可单用** | MIT |

## 三、为什么"直接套"不成立（技术硬理由）

1. **数据模型不匹配**：参考仓 UI 消费其自身事件类型（pi `AgentSessionEvent`、
   opencode `GlobalEvent`、zcode service descriptor）。UI 是数据模型的投影——
   换后端即重写投影层，而这层通常占壳的 30~50%（如 opencode 的
   `context/sdk.tsx + event.ts + sync.tsx`、pi-desktop 的 `agent-runtime` 189 文件）。
2. **操作面不匹配**：每个按钮/表单调用其自身后端 API（审批响应、会话切换、模型
   选择）——协议不同则全部适配。
3. **体量倒挂**：拿 327k~594k 行的壳去适配 40k 行的内核——适配层复杂度超过自研，
   且引入 React/Vite/Electron/SolidJS 工具链（我们当前零构建 UI）。
4. **许可边界**：pi-desktop 为 LGPL-3.0（摘代码分发须回馈修改）；claude-code 专有
   （只可读行为）。其余 MIT/Apache 可复制，但复制≠可用（见 1~3）。

## 四、三条可行路线的展开

### A. 不换壳、换打法（推荐用于 Web/桌面体验改善）

- **痛点归因**：23k 行原生 JS 手写 DOM——难在"每个交互都要手写状态同步/重渲染"，
  不是"没有壳可抄"。
- **做法**：引入 **preact + htm**（约 4KB，无需构建或仅 esbuild 打包）或 **lit**
  （Web Components，零构建），把交互层渐进组件化；样式与布局沿用现有 CSS。
- **收益**：保留全部既有资产（协议、i18n、图标、面板结构），只换渲染方式；
  不引入 Electron/框架全家桶。
- **成本**：中等、可分期（按面板逐个迁移，随时可停）。

### B. pi-tui 加终端形态（推荐用于快速见效）

- **为什么可行**：`pi-tui` 是**唯一"库形态"可独立拿**的 UI 资产——MIT、46 文件/
  19.5k 行、deps 仅 `get-east-asian-width` + `marked`、**不含任何 agent 依赖**。
- **做法**：写一个"四信封事件 → pi-tui Component 状态"的适配层 + 审批/输入
  组件映射（估计 1~2k 行）；内核与 host 完全不动（我们是分离进程形态，天然支持
  多前端）。
- **收益**：立刻获得一个功能完整的终端前端（pi/kimi/qwen 的 TUI 体验同源），
  且验证"多壳共用一内核"的架构承诺。
- **成本**：低（相对 A 更低且一次成型）。
- **注意**：pi-tui 是 MIT，复制需保留版权头并登记 THIRD_PARTY（项目既有纪律）。

### C. 借架构不借码（协议演进参考）

- codex `app-server` 的 req/notif/resp 分类与 pi-desktop `RACP` 的 WS+JSON-RPC
  设计，可作为我们四信封协议的演进参照（细节设计层面）；不引入其代码。

## 五、建议

1. **若目标是"尽快有一个像样的界面"** → 走 **B（pi-tui TUI）**：唯一低成本、
   可完整拿到的壳级资产，且与"内核 + 多前端"架构完全契合。
2. **若目标是"改善现有 Web/桌面 UI 的开发体验"** → 走 **A（轻量组件化重写交互层）**：
   治本，保留资产，渐进可停。
3. **不建议**任何"整体搬壳"路线（第二~三节理由）。

**下一步需要的信息**（决定 A/B 取舍）：当前"壳子难"具体难在——
① 样式/布局调试（如记忆中的布局 bug 量宽度链）？② 交互状态管理（手写重渲染）？
③ 功能缺口大（要补的功能多）？④ 打包/分发？四者对应不同方案（①②→A；③→B 或
先补功能；④→与壳无关的工程问题）。
