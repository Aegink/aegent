## 0. 一句话结论（先说结论）

参考仓的共同答案高度一致，与我方现状的落差集中在**一处**：

- **会话存储/事件词汇**：我方与 zcode/dsh 同属"事件溯源 sqlite + 闭集词汇表"阵营，**不重也不轻，
  基本对齐**；pi 走的是更极端的"通用持久文档内核（conversation/task/submission/document）"，
  是"0 骨架"的教科书形态（pi/durable 全程不出现 agent/LLM 词汇）。
- **子代理**：我方**有**（task 工具 + 后台上限 + task_wait/list/stop），比 dsh/zcode 少
  **续跑（resume）**与**send_message**两项寻址能力；pi 直接把 subagent 做成**插件**，
  pi-desktop 用 ADR 0279 补 resume，dsh 把 delegate/send_message/interrupt/list 拆成 3 个插件包。
- **多会话编排（核心落差）**：参考仓**全部把"模型发起编排"接到模型手上**——
  zcode 的 `Agent`/`SendMessage`/`ReadSessionContext` 工具、dsh 的 `workflow` 工具、
  pi-desktop 的 `SessionTask` 工具（官方插件）、agentscope 的 `_TeamAssign` 工具。
  **我方唯一入口是 settings op `collab-dispatch`，只有 UI 能触发；模型无任何编排/派发工具。**
  但参考仓同时给了我们另一条更重要的边界答案：**pi-desktop 把 orchestration 放在普通市场插件里，
  host-core 只留 `session/create` + `session/open` 两个原语 + 一份通信账本（ADR 0237/0239）**。
  即"模型可发起" ≠ "编排要在内核里"。
- **无人值守**：我方 cron/webhook/IM 齐备且都在 host/scheduler 域（**偏重**：4 个 host 文件 + 1451 行
  scheduler 全部编译进核）；参考仓 cron/bot 一律是 Host 服务 + **独立插件包**（dsh `tool-schedule`、
  hermes `cron/` + `gateway/platforms/`、zcode `services/bots`），且 dsh 有"模型自建提醒"工具而
  我方 cron 只有 UI op——**我方是"有渠道无模型入口"**。
- **记忆**：参考仓的记忆**几乎全在插件层**（hermes `plugins/memory/<name>/` + MemoryProvider 抽象；
  agentscope `middleware/_longterm_memory/`；zcode 是 memory/ 目录；pi/dsh 无记忆包）。
  我方只有 `save_memory` 一个工具 + MEMORY.md 单文件（**过轻**），且**内核没有任何记忆扩展点**
  （没有 provider 抽象，插件无法贡献记忆后端）。

**我方最重的 3 个问题**（详见 §7/§9）：
1. 编排能力"有引擎无方向盘"——collab 服务库 378 行 + 运行时 234 行齐备，模型却拿不到（P0）。
2. 子代理"能派不能续不能对话"——无 resume、无 send_message，重复委派重复付费（P1）。
3. 无人值守"有调度无模型入口 + 无渠道隔离"——cron 只有 UI op、IM 无 allowlist 且**写进固定会话**
   （P1，安全面）。

**读表结论**

1. "会话"在两个层次上被实现：**事件流层**（我方/zcode/dsh/hermes）与**通用持久文档层**（pi）。
   pi 的形态证明"会话原语"可以完全不含 agent 语义——`conversation`+`task`+`submission`
   三件套足以承载 agent 会话、子代理、后台任务、RPC 会话模型。
2. 迁移策略存在一个清晰的谱系（由轻到重）：
   `user_version 单调整数链`（我方，9 级）→ `SCHEMA_VERSION=31 + 列对账`（hermes）
   → `相邻格式链 + 每级冻结包 + catalog`（dsh，v0→v4 五个包）。
   我方在**机制上已经对齐 dsh 的纪律**（`migrate.ts:1-19` 头注释直接引 dsh·session-format/src/chain.ts），
   只差"冻结旧版本"这一条（我方迁移函数与代码同仓迭代，未冻结）。
3. **会话类型闭集**：只有 zcode 有（7 类，列值校验）。我方**没有**——`session_origins`（v9）
   只记父子血统、不记类型；`workflow_child`/`subagent_child`/`fork` 三类在我方分别由
   fork 事件、子会话 id 约定（`parent::task-N`）、origins 表**分散表达**，没有统一枚举。

**对照结论**

- 我方"31 类闭集 + 唯一逃生舱 + 编译期穷尽"是**比参考仓更严的设计**（zcode/dsh 都没有
  C16 那种 `AssertNever` 互差闸门），不是缺陷，不要为了"轻"而拆掉。
- 真正的差异是**版本化层级**：
  - pi 把版本放在**文档**上（每个 doc/entry kind 自带 version，演进=换定义版本、旧值冷载）——
    天然适合"内核不认识业务词汇"的插件生态；
  - dsh 把版本放在**格式**上（冻结迁移包）；
  - 我方把版本放在**库**上（单一 `user_version`）。
- 后果：我方**插件无法新增事件类型**（C15 双向钉死，只有 `plugin` 一个槽），
  于是插件想落"自己的状态"只能塞进 `plugin.payload`；而 zcode/dsh 的插件可以注册自己的
  事件/文档类型。这不是 bug（是刻意的封闭词汇表），但在"万物可插件"目标下是**扩展点缺口**
  （见 §8）。折中方案见 §9 C7。

### 4.2 编排的三层职责切分（参考仓共识）

把 ADR 0237/0239 + dsh 的包切分 + zcode 的两层拼起来，参考仓给出同一个三层答案：

| 层 | 职责 | 归属 | 我方对应物 |
|---|---|---|---|
| 原语 | 建会话 / 开会话 / 发 prompt / 观察 turn 终态 / 权限上限 | **内核或 host**（不得是插件） | `SessionStore.createSession`（db.ts:112）、`bridge.sendSystemPrompt`、`bridge.onEvent`、`permissionModeToCeiling`（collab-runtime.ts:32） |
| 账本 | 投递 id、源/目标会话、绑定真实 turn、状态机、完成回调（至多一次）、发起者身份校验 | **host 拥有**（持久、不可伪造） | `session/collab` 事件（双流四向）+ `session_origins` 表 + `collabId` |
| 工具 | 模型可见的 spawn/send/wait/list/stop 工具壳 | **插件**（pi-desktop 市场插件 / dsh tool-* 包） | **缺失**（只有 UI settings op） |

**我方现状与这层切分的差距**：原语 ✅ 有、账本 ✅ 有（甚至比 pi-desktop 更早做成事件双流），
**工具 ❌ 无**。即我方把"三生万物"里的编排，做成了"内核里的服务库 + UI 按钮"，
恰好落在参考仓明确否定的一侧（"Plugin settings must not become an authority for session identity,
authorization, or execution state" —— ADR 0239 Context）。

## 8. "必须留内核" vs "可外置" 判定 + 缺失扩展点

### 8.1 会话原语的分层判定（对应"一"与"二"）

| 能力 | 判定 | 理由（参考仓证据） |
|---|---|---|
| **事件存储 + append/flush/restore/snapshot** | **必须留内核（一）** | dsh `core/session` 由 persistence 插件挂载但仍以 `ctx.sessions` 为核心服务；我方/zcode/hermes 三家一致 |
| **事件词汇表框架（闭集校验 + 逃生舱 + 穷尽闸门）** | **必须留内核（0/一）** | dsh 的迁移链纪律、zcode 的类型校验都在核；pi 的 kind 开放是因为它有文档级版本兜底——我方没有，故闭集必须留 |
| **投影（project/coalescer/transcript/messages）** | **必须留内核（一）** | 事件→模型历史的唯一转换点，外置会让每个插件重做一遍 |
| **会话库 schema + 迁移链** | **必须留内核（0）** | 所有仓一致；但**运维表（audit/cron/titles/projects）应拆域**（见 C6） |
| **fork/lineage（会话谱系）** | 留内核，但降级为**通用 fork 原语** | pi 把它做成通用 `conversation` 复制（storage.fork + document copies），不含会话语义——我方 fork 已接近 |
| **子代理运行体（runner/深度/隔离）** | **可外置成插件（二）** | pi：subagent 是 extension（`subagent.ts:26`）；dsh：delegate 工具与 provider 都是独立包；**内核只需"能创建子会话 + 能投递 prompt + 能观察 turn 终态"** |
| **子代理生命周期工具（task/task_wait/list/stop）** | **可外置成插件（二）** | dsh tool-subagent + tool-subagent-control 是 3 个可裁包；pi-desktop 的 Task 家族是 core 工具集但**编排类工具 SessionTask 在插件** |
| **协作账本 + 权限上限快照 + 环检测** | **留内核/host（0/一）** | ADR 0239 明确"host owns durable ledger"、"plugins cannot supply a forged sender"、permission 是 host-owned |
| **编排工具（spawn/send/wait/supervise）** | **应外置成插件（二）** | ADR 0237 明确"ordinary marketplace plugin"；dsh 同 |
| **cron 引擎 + 持久表** | 引擎留 host 服务，**工具外置** | dsh：`ctx.schedule` 服务在 host，`schedule_*` 工具在 `tool-schedule` 插件 |
| **IM 渠道（飞书/Slack/…）** | **应外置成插件（二）** | hermes `gateway/platforms/`；zcode `services/bots`；两者都不是内核 |
| **记忆实现** | **应外置成插件（三）** | hermes `plugins/memory/<name>/` + MemoryProvider ABC；agentscope middleware |
| **goal 自主续跑驱动** | 可外置成插件 | dsh `goal-round-driver` 是独立包，且"omit it when each step requires human steering" |
| **会话检索（query/query-gateway）** | 服务留核，**工具外置** | dsh `session-query` 包组 + `tool-session-query` 插件分离 |

## 9. 候选方案（C1 ~ C9）

> 代号前缀 C 已用于"设计决策"（C14/C15…），为免混淆，本表方案代号用 **C-1…C-9**。
> 每项给：做什么 / 成本 / 风险 / 依赖。**本轮只出方案，不改码。**

### C-1 给编排装上方向盘：新增 `collab_dispatch` / `collab_send` 模型工具（P0）

- **做什么**：在 `kernel/tools/builtin/` 新增两个工具（或**一个** `collab` 工具 + action 枚举）：
  - `collab_dispatch{target?, createNew?, kind, content, notifyOnCompletion?}` → 调 `tryCollabSettingsOp` 等价的内部入口
    （现成：`src/host/collab-runtime.ts:157-173` 的 `dispatch`），`createNew:true` 时创建真实子会话；
  - `collab_send{targetSessionId, content}` → 对**已存在且被授权**的会话投递（走 EP-2）。
  权限：走既有 registry + chain 审批（**默认 ask** —— 跨会话写是敏感动作），
  并在 dispatch 时固化 `permissionCeiling`（已有机制 `permissionModeToCeiling` `collab-runtime.ts:32`）。
  工具描述必须写明"派发到另一会话会消耗对方上下文与预算"。
- **成本**：**小**（引擎全在：`collab-runtime.dispatch` + `createNew` + 回投；只差工具壳 + 装配接线 + 测试）。
- **风险**：**中**——模型可跨会话写。缓解：①默认 ask 审批；②目标必须已存在或由 createNew 显式创建；
  ③ceiling 快照机制已把降权/提权双向钉死；④环检测已在（`collaboration.ts:122`）；
  ⑤限流（每会话在途协作数上限，对齐 pi-desktop 4/16 与 ADR 0239 "bounds autonomous communication chains"）。
- **依赖**：无（可立即做）。**建议同时把工具本体设计成"可裁剪"**（插件可关），为 C-3 铺路。

### C-2 子代理续跑（resume）+ 双向 send_message（P1）

- **做什么**：
  1. `task` 工具加 `resume?: delegationId`：把上一轮该链的子会话历史作为上下文种子（我方子会话已是同 store 事件流，
     重放 `project` 即可），链键 = 子会话 id（delegationId → childSessionId 的稳定映射需从闭包注册表上提，见 EP-4）。
  2. 新增 `task_send{id, content}` 工具：向运行中的子会话**steer**（我方已具备 bridge 的 steer/队列语义），
     终态子会话则走 resume 重启。
- **成本**：**中**（resume 需要"子会话历史 → 子装配种子"的新装配路径 + 注册表上提；send_message 是 steer 通道复用）。
- **风险**：**低-中**——resume 的坑（pi-desktop ADR 0279 已踩过）：孤儿 tool 行、链式 id 解析、模型上下文形状。
  缓解：先做"只读历史种子"最小面，不做"完全重建"。
- **依赖**：EP-4（子会话注册/发现）建议先行。

### C-3 把编排/子代理工具拆成可裁剪插件包（P1，与 C-1/C-2 配套）

- **做什么**：把 C-1/C-2 的工具实现从 `kernel/tools/builtin/` 移到插件形态
  （我方已有 `plugin-manifest.ts` + inprocess/ws 两形态 loader），内核只留
  **EP-1/EP-2/EP-3/EP-4** 四个 host 原语接口。默认发行版内置该插件（体验不变），
  用户/preset 可关闭（对齐 dsh：`minimal` preset 不带任何 orchestration 工具）。
- **成本**：**中**（需要 EP-1..EP-4 四个接口先落地；工具外置本身机械）。
- **风险**：**低**（能力不减少，只是可裁剪；宿主 API 边界要设计好，否则插件绕过审批）。
  关键红线：**授权与权限上限必须留在 host**（不得让插件自己决定 ceiling），否则复制 ADR 0237 之前的老问题。
- **依赖**：C-1、EP-1~EP-4。

### C-4 记忆外置：EP-5 MemoryProvider + 把 save_memory 搬出去（P1，成本最小收益清晰）

- **做什么**：
  1. 内核加 `MemoryProvider` 抽象（initialize / systemPromptBlock / prefetch / syncTurn / tools / shutdown，
     同时只允许 1 个外部 provider——hermes 的双约束）；
  2. 内置 `builtin` provider = 现有 MEMORY.md 追加实现（**行为零变化**）；
  3. `save_memory` 工具随内置 provider 迁出 `kernel/tools/builtin/`，改由 provider 贡献。
- **成本**：**小**（内置实现已有，只加一层接口 + 装配）。
- **风险**：**低**（首个外部 provider 出现前，行为与今天一致）。注意：外部 provider 必须 fail-closed
  （prefetch 超时不得阻塞轮次；hermes 用 8s 超时 + daemon 线程兜底，可借）。
- **依赖**：插件贡献面需要支持"provider 注册"（现有 contributes 只有 tools/hooks/theme，需扩一类）。

### C-5 渠道外置：EP-6 Channel 接口 + 飞书/Slack 迁出内核（P2）

- **做什么**：定义 `Channel{authorize, handleInbound, deliverEvent}`；`im-feishu.ts`/`im-slack.ts`/
  `im-surface.ts` 迁到插件（或至少迁到"可裁剪内置插件"）；内核只留 webhook 路由 + 租约。
  **同时补 allowlist**（谁可以给这个 agent 发指令）——这是本期最重要的安全补强。
- **成本**：**中**（渠道已有清晰接口 `ImSurface`，迁出主要是装配改造 + 凭据注入路径）。
- **风险**：**中**——迁错会导致凭据读取/租约语义错位；IM 是外部输入面，必须保持 fail-closed。
- **依赖**：EP-6；建议与 C-6 一起做（同属"渠道/触达"域）。

### C-6 无人值守补强：调度工具外置 + 投递语义对齐 dsh（P1）

- **做什么**：
  1. 新增 `schedule_*` 模型工具（EP-7）：`schedule_create/list/update/delete`，
     由 preset 决定哪些 agent 有（默认**不给**，与 dsh minimal 一致）；
  2. cron 投递语义升级（三选一或组合）：投递前等目标会话 `flush` 确认 / 目标不在则**冷恢复** /
     错过只补最近一次 + deliveryHistory（对齐 dsh `schedule` 三纪律）；
  3. 保留现有 off-peak 队列（这是我方**强于**多数参考仓的一点，别删）。
- **成本**：**中**（引擎已有，主要是投递可靠性 + 工具 + 表字段：`cron_tasks` 需补 title/next_at/last_delivery 等）。
- **风险**：**低-中**（定时任务写库与会话库同库，注意 `cron_tasks` 归属应先做 C-7 的域拆分或明确"同库不同域"）。
- **依赖**：C-7（cron 表归属）、EP-7。

### C-7 会话库分域：运维表拆出"会话库"（P3，可以为不做）

- **做什么**：把 `audit_log` / `task_runs` / `cron_tasks` 从会话事件库（v4/v5 迁入的）拆到
  host 运维库（或至少拆到独立 schema/文件），会话库回到"只有会话事实"。
- **成本**：**中-大**（迁移 + 双库事务边界 + 现有读路径改造）。
- **风险**：**中**（数据搬迁；但"归档账本 + 导入注册表"语义清楚，可分两批）。
- **依赖**：无。**建议**：非必要不做；若要做，先做 `cron_tasks`（它最独立）。
  —— 与 §7 #8 对应，属"过重风险"，但**低于编排/记忆的优先级**。

### C-8 会话类型闭集（可选，P3）

- **做什么**：引入 `SESSION_TASK_TYPES`（interactive/fork/subagent_child/workflow_child/collab_child/…）
  作为**列值**（或 `session_origins` 加 kind 列），把今天分散在 fork 事件 / 子会话 id 约定 / origins 表的
  "会话种类"统一表述；写入点收敛到少数几处（fork/http create/collab createNew/subagent）。
- **成本**：**小-中**（列 + 校验 + 各创建点补写；迁移一个 v10）。
- **风险**：**低**（纯增量；清单/筛选消费面受益）。
- **依赖**：C-1（createNew 的类型语义会用到）。**收益**：会话列表可区分"我建的/派生的/子代理的"，
  与 pi-desktop `createdBySession/createdSessions` 投影同构。

### C-9 fan-out 脚本编排（**不建议本期做**，P3+）

- **做什么**：对齐 dsh `workflow` / zcode `CreateWorkflow`——模型写 JS/TS 脚本，
  `agent()/parallel()/pipeline()/phase()/log()` 在沙箱子进程里 fan-out 子代理。
- **成本**：**大**（沙箱运行时 + 脚本 API + 生命周期 + 取消/清理 + 权限传导）。
- **风险**：**高**（模型生成代码执行面 = 最大攻击面；需要沙箱、文件策略、深度/预算硬上限）。
- **依赖**：C-1/C-2/C-3 全部就绪（脚本编排是它们的上层组合）。
- **建议**：**先不排期**。理由：C-1 + 现有 task 后台委托已覆盖 80% 的 fan-out 场景；
  dsh 自己也把 `workflow` 描述为"only when the user explicitly requests a workflow"。
  记入备选，等 C-1/C-2 上线后有真实需求再做。
